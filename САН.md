## МАНИФЕСТ САН (ПОЛНЫЙ ТЕКСТ)

- **Версия:** 1.0-н
- **Дата утверждения:** 26 июля 2026 г.
- **Статус:** Утверждён Архитектурным комитетом Партнерства

**Связанные документы:**

- Системный архитектурный манифест (САМ)
- Манифест миграции
- Манифест Грек-Пантеон
- Манифест СУМКа

Настоящий документ является **Профильным Архитектурным Манифестом** платформы САН. Он **строго подчинен** Системному Архитектурному Манифесту (САМ), который имеет высший приоритет в случае любых противоречий. Данный манифест регулирует исключительно специфическую архитектуру платформы САН и является Единым Источником Правды (Single Source of Truth) только в рамках домена `can.blagorussia.ru`.

## 1. ГЕНЕРАЛЬНЫЙ АРХИТЕКТУРНЫЙ КАНВАС, МУЛЬТИОБЛАЧНАЯ АБСТРАКЦИЯ И СТАНДАРТЫ

Система САН проектируется как полностью независимая от конкретных провайдеров экосистема, построенная на принципах Evolutionary Architecture (развитие от $0 до промышленного масштаба без остановки системы) и Interface-Driven Development (изоляция бизнес-логики от конкретных сервисов через TypeScript-интерфейсы).

### 1.1 Спецификация Интерфейсов-Адаптеров (Инструкция для ИИ)

Прямые вызовы SDK сторонних вендоров (Supabase, Cloudflare, Yandex Cloud, Google Sheets) внутри бизнес-логики приложения **категорически запрещены**. Все внешние интеграции реализуются через паттерн «Адаптер» на основе TypeScript-интерфейсов.

Каждая ИИ-модель при генерации кода обязана оборачивать работу с внешними сервисами в следующие абстракции:

#### IStorageService (Уровень объектного хранения)

- **Методы:** `uploadFile(path: string, buffer: Buffer): Promise<string>`, `getFile(path: string): Promise<Buffer>`, `getFallbackUrl(path: string): Promise<string>`, `migrateFromBloggerToR2(): Promise<MigrationResult>`.
- **Примечание:** парсинг данных из файлов (например, JSON) в типизированные структуры должен выполняться на уровне бизнес-логики или ETL-процесса, а не внутри адаптера. Это обеспечивает соблюдение принципа единственной ответственности (SRP) и упрощает замену хранилища.

#### IBloggerImageStorage

**Методы:**

- `uploadToGallery(image: SanitizedImage, metadata: GalleryMetadata): Promise<string>` — загрузка изображения в Blogger-витрину
- `createThematicPage(topic: string, images: SanitizedImage[], yearMonth: string): Promise<string>` — создание тематической страницы (50 изображений)
- `getGalleryUrl(imageId: string): string` — получение URL изображения
- `backupMetadataToGit(): Promise<void>` — еженедельный бэкап метаданных

#### IGalleryExporter

**Методы:**

- `exportPropertyImages(propertyId: string): Promise<ExportResult>` — экспорт всех изображений объекта на gallery.obrazslov.ru
- `createThematicPage(topic: string, imageIds: string[]): Promise<string>` — создание тематической страницы на gallery.obrazslov.ru
- `syncMetadata(): Promise<void>` — синхронизация метаданных с gallery.obrazslov.ru

#### IPrimaryDataGateway (Уровень первичного сбора и ETL)

- **Методы:** `ingestRawData(source: string, rows: RawRow[]): Promise<void>`, `getPendingObjects(): Promise<RawRow[]>`, `markProcessed(id: string): Promise<void>`.
- **Реализация Этапа-1:** `GoogleSheetsAdapter` – использует Google Sheets API для чтения/записи структурированных данных.
- **Реализация Этапа 0:** `MinIOETLAdapter` – управляет сырыми данными, хранящимися в локальном MinIO (S3-совместимое хранилище) в виде сжатых JSON-файлов.
- Google Таблицы на Этапе 0 используются исключительно для ручного управления конфигурациями (`config_sheet`) и как вспомогательный интерфейс для администратора, но не для хранения больших объёмов сырых данных парсинга.
- **Эволюция на Этапах 1-2:** Переключение на Yandex Object Storage или любой другой S3-совместимый бакет с сохранением тех же интерфейсов.

#### IPDNGateway (Уровень первичной локализации персональных данных в РФ по 152-ФЗ)

- **Методы:** `processAndRoute(pdnData: RawPdnInput): Promise<SecurePayload>`.
- **Реализация Этапа 0:** `YandexServerlessGateway` (использует бесплатные лимиты Yandex Cloud Functions для фиксации первичного сбора персональных данных на территории РФ).
- **Эволюция на Этапах 1-2:** Переключение на `SelfHostedNodeGateway`, развёрнутый на собственном российском VPS на базе Docker/K8s.

#### IPropertySearch (Уровень поискового движка каталога)

- **Методы:** `search(filters: SearchFilters): Promise<PaginatedResult<Property>>`.
- **Реализация Этапа-1:** `GoogleSheetsSearchService` – выполняет фильтрацию по загруженным в память данным из Google Sheets (с ограниченной производительностью, но достаточной для 3 000 объектов).
- **Реализация Этапа 0:** `PostgresFullTextSearchService` – выполняет полнотекстовый поиск по полям `address`, `description` с использованием GIN-индекса на `tsvector` (конфигурация `russian`), geo-поиск через `ST_DWithin` с GIST-индексом.

#### IInfrastructureProvider (Уровень сбора данных об окружении)

- **Методы:** `fetchInfrastructure(coords: {lat: number, lng: number}, radiusMeters: number): Promise<InfrastructureData>`, `fetchOfficialRegulations(cadastralNumber?: string, address?: string): Promise<OfficialRegulationData>`.
- **Реализация Этапа-1 (пилотный режим, 5–10 объектов):**
  - `OSMOverpassAdapter` – использует Overpass API OpenStreetMap для получения POI (бесплатно, без ключа).
  - `DomRFAPIAdapter` – интеграция с API ДОМ.РФ (бесплатно, требуется регистрация).
  - `GovSiteParserAdapter` – скачивание PDF-документов с региональных сайтов и сохранение в MinIO.
  - `DeveloperSiteParserAdapter` – парсинг страниц застройщиков для извлечения обещанной инфраструктуры.
- **Реализация Этапа 0 (полноценный режим, до 200 объектов):** те же адаптеры с расширенным охватом, добавлением кэширования и мониторинга квот.
- **Эволюция Этапов 1-2:** замена на адаптеры с локальным дампом OSM и Redis-кэшированием.

#### IReviewProvider (Уровень агрегации отзывов из внешних сервисов)

**Методы:**

- `fetchReviews(entityId: string, entityType: 'agent' | 'agency'): Promise<Review[]>`
- `fetchAggregateRating(entityId: string): Promise<AggregateRating>`
- `publishReview(review: NewReview): Promise<Review>` (только для internal provider)
- `subscribeToUpdates(entityId: string, callback: (review: Review) => void): Promise<void>`

**Реализации Этапа 0:**

- `InternalReviewAdapter` — работа с собственной БД САН (верифицированные отзывы клиентов через `client_requests` и `cooperative_deals`).

**Реализации Этапа 1:**

- `TwoGisReviewAdapter` — Firm API 2ГИС.
- `FlampReviewAdapter` — API Flamp.
- `AggregatingReviewService` — объединяет данные из всех провайдеров с весовыми коэффициентами.

**Эволюция Этапа 2:** парсинг Отзовик/IRecommend, интеграция с Profi.ru.

#### IImageProcessorService (Обработка медиа)

- **Реализации:** `SharpAdapter` (pHash, композиция слоев), `GeminiVisionAdapter` (классификация).

#### IAiSearchGateway (Интеграция с ИИ-ассистентами)

- **Реализации:** `RuLocalizationAdapter` (Этап 0), `EnLocalizationAdapter` (Этап 1), `ArLocalizationAdapter` (Этап 2).

#### ISlugGenerationService (Генерация и разрешение SEO-friendly URL)

**Методы:**

- `generatePropertySlug(property: PropertyContext): Promise<string>` — генерирует ЧПУ на основе нормализованного адреса и `listing_key`.
- `resolveSlugToId(slug: string): Promise<string | null>` — разрешает slug обратно в ID объекта для маршрутизации.
- `handleCollision(slug: string, listingKey: string): Promise<string>` — обработка коллизий при совпадении адресов.
- `buildBreadcrumbPath(locationGeoId: string): Promise<BreadcrumbItem[]>` — построение иерархии хлебных крошек на основе `locations_geo`.

**Реализация Этапа 0:** `PostgresSlugService` (работа с таблицей `property_seo_map` + кэш в Node.js Map).

**Формула ЧПУ (Global MLS Standard):** `/{country_code}/{region_slug}/{city_slug}/{district_slug}/{street_slug}-{building_number}-{unit_type}{unit_number}/{listing_key}`.

**Примеры:**

- 🇷🇺 РФ: `/ru/voronezh/central/koltsovskaya-35-kv12/MLS-84729`
- 🇺🇸 США: `/us/ny/new-york/5th-ave-apt-4b/MLS-99210`
- 🇬🇧 Великобритания: `/uk/london/kensington/high-st-flat-4/MLS-11029`

`listing_key` — это `external_id` или `cadastral_number`, гарантирующий уникальность и вечность URL (Evergreen URL).

#### IRESODataMapper (Маппинг внутренних моделей САН в стандарт RESO Data Dictionary)

**Методы:**

- `mapLookupValue(resoFieldName: string, resoValue: string): Promise<number>` — маппинг справочников (например, `'NewConstruction'` → `1`).
- `toResoMember(internalAgent: AgentContext): Promise<ResoMemberDTO>` — маппинг агента в RESO Member.

**Реализация Этапа 1:** `ResoDataMapperService` (набор JSON-конфигов, хранящих соответствие между RESO-строками и САН-smallint).

**Назначение:** обеспечение бесшовной B2B-интеграции с мировыми CRM (Salesforce, HubSpot, amoCRM, Битрикс24) и зарубежными порталами (Zillow, Rightmove) через стандартные RESO-коннекторы.

#### IVideoMultiPublisherService (Мульти-загрузка видео на внешние платформы)

**Методы:**

- `publishToAll(videoFile: Buffer, metadata: VideoMetadata, brand: Brand, platforms: VideoPlatform[]): Promise<PublishResult[]>` — параллельная загрузка видео на все указанные платформы.
- `selectPlatforms(contentType: ContentType, stage: Stage): VideoPlatform[]` — умный выбор платформ по типу контента и этапу развития.
- `fetchOEmbed(videoUrl: string): Promise<VideoMetadata>` — извлечение метаданных через oEmbed API.
- `generateVideoObjectJsonLd(metadata: VideoMetadata): string` — генерация JSON-LD разметки VideoObject.

**Реализация Этапа 0:** `VideoMultiPublisherService` с адаптерами для VK Video, Rutube, Dzen, YouTube.

**Поддерживаемые платформы:**

- **VK Video** — основной для новостного и парсингового контента (бесплатный безлимит, oEmbed).
- **Rutube** — федеральный стандарт для экспертного контента (бесплатный безлимит, oEmbed).
- **Яндекс Dzen** — приоритет для Яндекс.Нейро и SEO (бесплатный безлимит, частичный oEmbed).
- **YouTube** — международное зеркало для B2B-экспансии (бесплатный безлимит, oEmbed).
- **Vimeo (P2)** — премиум-контент без рекламы (500 МБ/неделю на Basic).
- **Dailymotion (P2)** — европейская аудитория (бесплатный безлимит).
- **Internet Archive (P2)** — вечное архивное хранение (бесплатный безлимит).

**Архитектура «Двух Брендов»:**

- **Бренд 1:** НКО «Общественное благополучие» — для 11 сайтов основной сети (blagorussia.ru, obrazslov.ru, partnerstvo, novosti, ot-gorozan, obavlenia, interesnye-mesta, moisites, joga, ideologia, grekpanteon).
- **Бренд 2:** САН — для платформы can.blagorussia.ru.
- **Бренд 3 (опциональный, P1):** partnerstvo.blagorussia.ru и novosti.blagorussia.ru — если контент требует смыслового отделения.

**Видео-Матрица РФ (Content-Based Routing):**

| Тип контента | Primary (РФ) | Mirror (Международный) |
|--------------|--------------|------------------------|
| Аналитика, Блоги, Grekpanteon | Dzen (приоритет) или Rutube | YouTube |
| Новости, RSS-агрегаторы | VK Video | YouTube |
| Карточки объектов САН | VK Video (быстрый плеер) | YouTube |
| Образовательный (joga, ideologia) | Dzen, Rutube | YouTube |

**Двойное зеркалирование (Dual-Source Mirroring):** Каждое видео автоматически публикуется одновременно в Primary-источник (по Видео-Матрице) и в YouTube (зеркало).

**JSON-LD VideoObject:** Генерируется с массивом `uploadUrl` (все платформы), `thumbnailUrl`, `uploadDate`, `description`, `regionsAllowed`.

#### ISocialDistributionService (Управление публикациями в социальных сетях)

**Методы:**

### 1.2 Стандарты данных и протоколы

Для обеспечения интероперабельности и соответствия мировым практикам, все публичные API и форматы обмена данными должны соответствовать следующим стандартам:

- **RESO Web API Core 2.0** – основной стандарт для операций CRUD над объектами недвижимости, определений полей и классификаторов. Все эндпоинты, предоставляющие данные о листингах, должны быть совместимы с RESO Data Dictionary.
- **OData протокол (версия 4.0)** – используется для запросов с фильтрацией, сортировкой, пагинацией и выборкой полей. Дополнительно поддерживается оператор `$expand` для включения связанных сущностей.
- **OAuth2** (с поддержкой `grant_type=client_credentials` и `authorization_code`) – единый протокол авторизации для всех внешних приложений и партнёров.

**RESO Certification Compliance (Этап 1)** — публичный API САН (`/api/v1/reso/`) обязан поддерживать базовый синтаксис OData v4.0:

```text
$filter=ListPrice gt 5000000 and City eq 'Воронеж'
$select=ListingKey,ListPrice,BuildingName
$expand=Media,Agents
$top=50&$skip=100
```

**Мульти-валюта и мульти-язык** — в `ResoListingDTO` обязательны поля `ListPriceCurrencyCode` (ISO 4217) и `LanguageCode` (ISO 639), что позволяет САН легально работать с объектами в разных странах (ОАЭ, Таиланд, ЕС), автоматически конвертируя цены на уровне API-адаптера.

### 1.3 Гибридная модель хранения данных (Hybrid Storage Engine)

Для соблюдения жёсткого лимита бесплатного плана Supabase (500 МБ) и обеспечения экономичности на этапе 0 данные разделены на четыре физических слоя:

#### Реляционное ядро (Supabase / PostgreSQL)

Хранит только строго типизированные поисковые поля: ID объектов, связи с агентствами и агентами, статусы, цены, площади, комнаты, адрес (улица, номер дома), гео-координаты (PostGIS), внешние ссылки (`external_id`). Средний размер строки — до 200 байт. Потолок в 50 000 объектов занимает не более ~10 МБ данных + индексы (~30 МБ). На этапе 0 таблица `property_price_history` не создаётся — история цен хранится во внешнем слое сырых данных (см. ниже).

В структуру `properties` добавляются поля `main_image_url text` и `media_passport_path text`. Длина путей жестко лимитирована (макс. 60 символов) для соблюдения правила 200 байт. Полный медиа-паспорт выносится в MinIO.

Добавлено поле `cadastral_number varchar(30) NULL` с UNIQUE-индексом для сквозной дедупликации.

#### Слой сырых данных (MinIO / S3)

Каждый застройщик или источник имеет отдельную папку в MinIO, где хранятся сжатые JSON-файлы с колонками, соответствующими полям RESO/САН.

История цен хранится как массив `price_history` внутри JSON-объекта каждого объекта недвижимости.

Доступ осуществляется через адаптер `MinIOETLAdapter`.

**Двухэтапная дедупликация в ETL-процессе:**

1. На этапе первичного ETL: суррогатный ключ `md5(source_domain + normalized_address + unit_number)` для квартир/помещений или `cadastral_number` для земельных участков.
2. На этапе реляционного ядра (при UPSERT): дедупликация по физическому бизнес-ключу (`building_id`, `unit_number`) или `cadastral_number`.

**Асинхронная валидация:** после сохранения в сырую таблицу записи проходят фоновую валидацию на соответствие Data Contract. Невалидные записи — в Dead-Letter Queue (таблица `etl_failed_rows`).

#### Объектный слой (Эволюционная модель)

| Этап | Blogger | R2 |
|------|---------|----|
| -1/0 | Основное хранилище изображений (безлимит при ресайзе ≤1600px) | Только PDF и media_passport.json.gz |
| 1+ | Архив (вечное хранение) | R2 + CDN — LCP-ускорение для главных изображений карточек САН |

Переход с Этапа 0 на Этап 1 — по решению Архитектурного Комитета (ручной триггер).

> **ВАЖНО:** Хранение видеофайлов в Cloudflare R2 **категорически запрещено**.

#### Слой инфраструктурных данных (MinIO / S3)

Выделенная папка `infrastructure/` в MinIO для хранения собранных данных об окружении, исходных PDF-документов с госсайтов и сгенерированных ИИ-описаний.

На Этапе-1 вместо слоёв 1 и 2 используется Google Таблицы как временное реляционное ядро и хранилище сырых данных.

### 1.3.5 Требования к хостингу САН

Платформа САН использует Next.js App Router с SSR (Server-Side Rendering), Edge Middleware (для WAF и фасетной отсечки) и серверными компонентами.

**ЗАПРЕЩЕНО** развёртывание САН на GitHub Pages (не поддерживает SSR/Middleware).

**Допустимый вариант:** Vercel (PaaS) под аккаунтом `can-secure-dev`.

**DNS:** `can.blagorussia.ru` → CNAME на `cname.vercel-dns.com`.

**Соответствие 152-ФЗ при использовании Vercel:**

1. Vercel используется исключительно для рендеринга UI, SSR и Edge Middleware.
2. Персональные данные НЕ обрабатываются на edge-узлах Vercel и не кэшируются в их CDN.
3. Весь конвейер ПДн проходит через российский ПДн-шлюз на Yandex Cloud Functions (§4.1): сбор → шифрование AES-256-GCM → передача зашифрованного `bytea` в Supabase.
4. На стороне Next.js (Vercel) расшифровка происходит только в runtime для авторизованных пользователей, ключи хранятся в `.env` (Vercel Environment Variables), доступных только серверным функциям.
5. Edge Middleware не имеет доступа к ключам шифрования и работает только с публичными данными (фильтры каталога, SEO-маппинг).
6. **Аудит:** Все операции расшифровки логируются в `pdn_access_log`.

### 1.4 Стратегия ухода от PaaS-ограничений (план миграции базы данных)

**Этап-1 (Старт с Google Sheets):** Используются Google Таблицы как основное хранилище структурированных данных (до 3 000 объектов — жёсткий лимит). Превышение этого лимита приведёт к деградации API и памяти Next.js.

**Этап 0 (Бесплатный Supabase + MinIO):**

- Использование бесплатного облачного инстанса Supabase Cloud Free (ограничение 500 МБ, 20 одновременных соединений).
- ИИ генерирует миграции, используя только стандартные возможности PostgreSQL и расширения PostGIS, pgcrypto и pg_trgm. Запрещено использование специфических проприетарных фич Supabase.
- Развёртывание MinIO в локальном Docker-контейнере как S3-совместимого хранилища для сырых данных.
- Переход на Supabase Pro ($25/мес) выполняется ТОЛЬКО при превышении 20 одновременных соединений или при росте БД > 400 МБ.
- **ЗАПРЕЩЕНО** использование pgvector на Этапе 0. Альтернатива: семантический поиск через smallint[] теги-синонимы (Раздел 17).

**Этапы 1-2 (Масштабирование):**

- Бесшовная миграция ядра на Self-hosted Supabase или чистый PostgreSQL (Yandex Managed Service for PostgreSQL).
- Слой сырых данных переключается с MinIO на промышленное S3-хранилище (Yandex Object Storage).
- Поисковый движок (при необходимости) переключается на Typesense/Elasticsearch на VPS.

### 1.5 Локальная in-memory оптимизация (Отказ от избыточного Redis)

- **SEO-редиректы старого сайта:** карта соответствия старых URL и облака тегов хранится в статическом компилируемом JSON-файле `migration_seo_map.json` внутри проекта Next.js.
- **Внешний Redis** подключается на Этапах 1–2 только для динамического кэширования сотен тяжёлых фидов Авито/ЦИАН и для сессий пользователей.

**In-Memory кэширование тяжёлых запросов:**

Для снижения нагрузки на базу данных и внешние хранилища на Этапе 0 реализуется гибридный подход к кэшированию, исключающий риск OOM и "cache thrashing":

- Статические / справочные данные (SEO-карты, `system_enums`, конфигурации) хранятся в памяти Node.js (Map / node-cache). Лимит: до 50 МБ.
- Тяжёлые выборки (результаты поиска, инфраструктурные паспорта, фиды) кэшируются с использованием Next.js Data Cache (с хранением на диске/в SQLite внутри контейнера) или локального Valkey/Redis, запущенного в том же Docker-контейнере, что и MinIO (что не требует внешних PaaS).
- Жёсткие лимиты для RAM-кэша Node.js: `maxKeys = 5000`, `maxMemory = 100 МБ`.
- Кэш ПДн: TTL строго не более 1 минуты, хранение только в изолированном RAM-контейнере с немедленной очисткой.

**Типы кэшируемых данных:**

- Результаты поиска по каталогу — TTL = 5 минут.
- Сгенерированные фиды (XML/RSS) — TTL = 1 час.
- Геокодированные адреса — бессрочное кэширование.
- Кэширование классификаторов: таблица `system_enums` полностью загружается в память при старте приложения.
- История цен — TTL = 1 час при чтении из MinIO.
- Данные об окружении — TTL = 1 час при чтении из MinIO.
- SEO-маппинг — таблица `property_seo_map` кэшируется в Node.js Map с TTL = 15 минут. Инвалидация — при изменении адреса или статуса объекта.
- Видео-метаданные — oEmbed-данные кэшируются с TTL = 24 часа.

**Триггер мгновенной инвалидации:** При получении события от вебхука видео-платформы (или при ручном удалении видео администратором) кэш oEmbed для конкретного `video_id` инвалидируется немедленно. Это заставляет маску деградации сработать мгновенно, а не через 24 часа.

**Механизм инвалидации:**

- При создании/обновлении/удалении объекта через API кэш соответствующих поисковых запросов и фидов помечается как устаревший (инвалидация по тегам).
- В качестве библиотеки используется `node-cache` или встроенный `Map` с автоматической очисткой по TTL.
- При кэшировании ПДн данные сохраняются только в зашифрованном виде. Кэш ПДн имеет TTL не более 1 минуты.

## 2. СКВОЗНОЙ КОНТРАКТ ДАННЫХ САН (DATA CONTRACT)

Система базируется на международном стандарте RESO Web API Core 2.0 (Data Dictionary), адаптированном под специфику рынков САН.

### 2.1 Иерархия сущностей данных

#### Уровень 0: Географический справочник (locations_geo)

Содержит плоские уникальные строки: Страна → Регион → Район → Город/Населенный пункт.

Добавлено поле `country_code VARCHAR(5) NOT NULL DEFAULT 'RU'` с индексом для поддержки международной локализации и построения хлебных крошек.

#### Уровень 1A: Здание (buildings)

Ссылается на `locations_geo`. Хранит адрес, этажность, год постройки, ссылки на PDF-документы, профиль Наш.Дом.РФ и гео-точку PostGIS.

#### Уровень 1Б: Земельный участок (land_plots)

Существует параллельно зданиям, ссылается на `locations_geo`. Хранит площадь в сотках, кадастровый номер и гео-координаты участка.

#### Уровень 2: Помещение или Заявка (properties)

Ссылается на `buildings` (или `land_plots`). Хранит номер помещения, цену, площадь, число комнат и системные классификаторы. Все расширенные поля хранятся во внешних слоях (MinIO / R2), а в `properties` — только ссылка на `external_id`.

В `properties` добавляется поле `infrastructure_updated_at timestamp` — указывает, когда были последний раз обновлены данные об окружении для этого объекта.

История цен — на этапе 0 не создаётся таблица `property_price_history`. Вместо этого история хранится в MinIO как часть сырых данных.

**Кадастровый ID как сквозной ключ дедупликации:**

### 3.2 Система рейтинга агентов и типы агентов

Рейтинг агента (значение от 0 до 5) является основным механизмом распределения лидов.

**Базовый рейтинг (от 0 до 4,5)** – вычисляется автоматически на основе:

- количества успешно закрытых сделок;
- средней скорости закрытия;
- отзывов коллег по Сообществу (верифицированных);
- внешних отзывов (применяется только с Этапа 1): агрегированный рейтинг из Яндекс.Бизнес, 2ГИС и внутренних отзывов САН. Формула: `External_Rating_Component = (yandex_rating × 0.8 + 2gis_rating × 0.7 + internal_rating × 1.0) / 2.5`. Компонент учитывается в базовом рейтинге с весом 20%. Минимальное количество отзывов для учета: 5.
- На Этапе-1 и Этапе 0 используется упрощённая формула: `External_Rating_Component = internal_rating` (только верифицированные внутренние отзывы САН).

**Дополнительные бонусы (суммарно не более +0,5 балла)** – начисляются за:

- Работа в агентстве-партнёре — бонус +0,2.
- Участие агентства в коллективном фонде продвижения — +0,1.
- Личный статус «Привилегированный агент» — +0,15.

**Нематериальные бонусы** (добавляются администратором по решению Комитета):

| Статус | Критерии присвоения | Бонус | Период действия |
|--------|---------------------|-------|-----------------|
| Эксперт рынка | Написание ≥5 аналитических статей за 6 месяцев | +0,1 | 6 месяцев |
| Наставник | Проведение ≥3 вебинаров за год | +0,1 | 1 год |
| Хранитель сообщества | Участие в разрешении ≥5 арбитражных споров | +0,05 | 1 год |

**Правило замораживания статуса при штрафах:** Если на Привилегированного агента (рейтинг ≥ 4,50) накладывается временный штраф, снижающий его значение ниже 4,50, его статус и право участия в текущих коллективных фондах продвижения замораживаются только со следующего расчётного периода (месяца).

**Механизм меритократических санкций:**

В хранимую процедуру расчета рейтинга внедряется условие проверки штрафа за контентный фрод:

1. Период действия штрафа: 90 дней. Восстановление возможно только по решению Арбитража САН.

| 1 | Member | Участник САН |

| 3 | Certified | Сертифицированный (резерв) |

### 3.3 Логика Некоммерческого Финансирования и Модель Возмещения Затрат

Все денежные поступления в САН оформляются как добровольные целевые взносы участников в специализированные фонды. Это позволяет направлять средства на конкретные нужды (оплата сотовой связи, закупка оргтехники, расходных материалов, хостинг, развитие ПО) без уплаты налога на прибыль, в соответствии с соглашениями о некоммерческом сотрудничестве.

> **Важно:** Ежегодные целевые взносы Агентств-партнёров и взносы по парсинговым сделкам распределяются в разные фонды САН:

1. **Фонд юридической защиты** (`target_fund = 1`) — формируется из ежегодных целевых взносов Агентств-партнёров (1 000 руб./агент/год). Направляется на правовую защиту агентов, разрешение внутренних конфликтов, арбитражные разбирательства.
2. **Фонд инфраструктуры парсинга** (`target_fund = 2`) — формируется из отчислений по парсинговым сделкам (5–10% от целевого вознаграждения). Направляется на покрытие затрат: хостинг, API-сервисы, ИИ-генерация, модерация, хранение данных в MinIO.
3. **Фонд развития платформы** (`target_fund = 3`) — формируется из возмещения затрат от совместных коллективных фондов продвижения и других источников. Направляется на развитие функционала платформы.
4. **Фонд продвижения** (`target_fund = 4`) — формируется из добровольных взносов участников коллективных фондов продвижения.

Финансовый баланс ведётся в таблице `agencies` в поле `balance_cents` (bigint, учёт в копейках) и пополняется по основным каналам:

1. **Ежегодный фиксированный взнос** — списывается автоматически раз в год из расчёта 100 000 копеек (1 000 руб.) за каждого активного агента, числящегося в агентстве. Для привилегированных агентов — с их персонального кошелька. Направляется в фонд юридической защиты.

**Отчисления по парсинговым сделкам:**

При успешном закрытии сделки по объекту, импортированному парсерами (где `source_id > 0`), производится целевое возмещение затрат САН на инфраструктуру парсинга (5–10% от целевого вознаграждения агента, настраивается в `config_sheet`).

**Кто производит отчисления:**

1. Отчисления по парсинговым сделкам производятся ВСЕГДА, независимо от статуса агентства. Разница лишь в том, кто производит отчисления:
   - Если агент указан как сотрудник Агентства-партнёра (`agency_role = 1`) и агент НЕ выбрал самостоятельную оплату (`pay_parser_fees_independently = false`): отчисления производит Агентство-партнёр со своего баланса.
   - Если агент НЕ указан как сотрудник Агентства-партнёра (свободный агент или работает в NonPartner-агентстве): отчисления производит сам агент со своего персонального баланса.
   - Агент может самостоятельно производить отчисления даже если он указан как сотрудник Агентства-партнёра (установив `pay_parser_fees_independently = true`). В этом случае отчисления списываются с персонального баланса агента и НЕ фиксируются за Агентством-партнёром.

**Обоснование:** Отчисления по парсинговым сделкам — это возмещение затрат на инфраструктуру парсинга (хостинг, API, ИИ-генерация, хранение данных). Эти затраты несёт САН независимо от статуса агентства. Поэтому отчисления производятся ВСЕГДА по парсинговым сделкам, но источник оплаты зависит от того, кто указан как ответственный за агента.

**Формула расчёта:**

1. Если сделка парсерная (`source_id > 0`):
   - `san_platform_share = san_platform_share_percent` (по умолчанию 5%)
   - **Кто платит:**
     - Если `agent.agency.agency_role = 1` (Partner) И `agent.pay_parser_fees_independently = false`: payer = agent.agency (Агентство-партнёр). Списание с баланса агентства → `target_fund = 2` (фонд инфраструктуры парсинга).
     - Иначе (NonPartner, свободный агент, или `pay_parser_fees_independently = true`): payer = agent (сам агент). Списание с персонального баланса агента → `target_fund = 2`.
2. Если сделка НЕпарсерная (`is_manual_override = true`):
   - `san_platform_share = 0%` (отчисления не производятся).

**Примеры:**

- Агент А работает в Агентстве-партнёре, сделка парсерная, целевое вознаграждение 100 000 руб. → возмещение САН = 5 000 руб. (5%), платит Агентство-партнёр.
- Агент Б работает в NonPartner-агентстве, сделка парсерная, целевое вознаграждение 100 000 руб. → возмещение САН = 5 000 руб. (5%), платит сам агент.
- Агент В — свободный привилегированный агент, сделка парсерная, целевое вознаграждение 100 000 руб. → возмещение САН = 5 000 руб. (5%), платит сам агент.
- Агент Г работает в Агентстве-партнёре, но выбрал самостоятельную оплату → возмещение САН = 5 000 руб. (5%), платит сам агент (не фиксируется за агентством).
- Агент Д работает в Агентстве-партнёре, сделка НЕпарсерная (ручной ввод) → возмещение САН = 0 руб.

**Настройка в системе:**

- В таблице `agents` добавлено поле `pay_parser_fees_independently` (boolean, default false) — флаг самостоятельной оплаты отчислений по парсинговым сделкам.
- Если `pay_parser_fees_independently = true`, отчисления всегда списываются с персонального баланса агента, даже если он работает в Агентстве-партнёре.

**Возмещение затрат от совместных коллективных фондов продвижения** — САН удерживает 10% от сэкономленной суммы. Направляется в фонд развития платформы.

**Автоматизация:**

1. Расчёт балансов и списаний выполняется хранимой процедурой, запускаемой по расписанию (cron/Inngest).
2. Все операции логируются в таблицу `transaction_log` (кто, когда, сумма, тип операции, целевой фонд) для аудита.
3. При отрицательном балансе (`balance_cents < 0`) все объекты агентства/агента автоматически переводятся в статус Pending до пополнения.
4. Исключение: Если баланс стал отрицательным в результате списания административной комиссии за отзыв согласия (п. 9.4.4), блокировка объектов в статусе Pending переносится на 1-е число следующего расчётного месяца.

**Публичный дашборд расходов:**

Для обеспечения прозрачности все поступления и расходы фондов агрегируются и отображаются на специальной публичной странице `/transparency`. Дашборд содержит ежемесячные отчёты с детализацией по категориям и по фондам (юридическая защита, инфраструктура парсинга, развитие платформы, фонд продвижения).

Аудит расходов проводится независимым ревизором, избираемым сообществом раз в год.

**Модуль финансовой отчётности в личном кабинете:**

Каждый агент и представитель агентства имеют доступ к финансовому дашборду, отображающему:

1. Текущий баланс с разбивкой по типам средств.

5. Все финансовые операции защищены двухфакторной аутентификацией для подтверждения крупных транзакций (свыше 10 000 руб.).

## 4. БЕЗОПАСНОСТЬ, ЛОКАЛИЗАЦИЯ ПЕРСОНАЛЬНЫХ ДАННЫХ В РФ (152-ФЗ) И УВЕДОМЛЕНИЯ

### 4.1 Конвейер обработки ПДн

- **Шаг А. Сбор на российском шлюзе** — Yandex Cloud Functions.
- **Шаг В. Первичное хранение и логирование** — Yandex Cloud фиксирует факт сбора.
- **Шаг С. Передача в ядро с шифрованием** — Бэкенд Next.js выполняет шифрование полей `phone` и `email` перед записью в БД, используя AES-256-GCM. В базу данных записывается только зашифрованный буфер (`bytea`). Использование SQL-функции `pgp_sym_encrypt()` запрещено.

Пример реализации на Node.js:

```javascript
const crypto = require('crypto');
const algorithm = 'aes-256-gcm';

const encrypt = (text, secret) => {
  const iv = crypto.randomBytes(16);
  const cipher = crypto.createCipheriv(algorithm, Buffer.from(secret, 'hex'), iv);
  let encrypted = cipher.update(text, 'utf8', 'hex');
  encrypted += cipher.final('hex');
  const authTag = cipher.getAuthTag().toString('hex');
  return { encrypted, iv: iv.toString('hex'), authTag };
};
```

- **Шаг D. Контролируемый доступ** — API расшифровывает данные только для авторизованных пользователей.
- **Аудиторский след** — все операции расшифровки логируются в `pdn_access_log`.

### 4.2 Дополнительные меры

- Двухфакторная аутентификация для администраторов.

## 5. ИИ-АРХИТЕКТУРА, КОНВЕЙЕР ПАРСИНГА, САМООБУЧЕНИЕ, УПРАВЛЕНИЕ КАЧЕСТВОМ ДАННЫХ И АВТОМАТИЧЕСКАЯ АНАЛИТИКА РЫНКА

### 5.1 Конвейер ИИ-парсинга

**Шаг 1. Инициация и анализ**

Администратор вставляет массив ссылок. Система проверяет домен в таблице `parser_domain_templates`.

**Шаг 2. Согласование схемы**

Администратор утверждает маппинг, система выполняет UPSERT в `parser_domain_templates`. При маппинге полей парсера в `mls_mapping_json` добавляется обязательное поле `construction_status` с автоматическим определением:

- Если в источнике указан «застройщик», «ЖК», «новостройка», «сдача в N квартале» → код 1 (NewConstruction)
- Если в источнике указаны «вторичка», «КУМИ», «гос-торги», «извещение», «аукцион» → код 2 (Resale)
- Если не удаётся определить автоматически → объект помечается как Pending для ручной классификации.

**Шаг 3. Асинхронный сбор данных**

Загрузка страниц, извлечение данных по шаблону, сохранение в MinIO.

**Шаг 4. Самообучающийся инспектор и валидация**

При обработке новой ссылки выделяется домен, выполняется запрос к `parser_domain_templates`.

#### 5.1.4. Валидация текстовых полей клиентских заявок

При создании или обновлении записи в таблице `client_requests` система выполняет сканирование полей `description` и `address_text` на наличие паттернов телефонных номеров, email-адресов и других персональных данных.

Если потенциальные контакты обнаружены, операция блокируется.

Проверка выполняется на бэкенде до шифрования и сохранения в БД.

**Шаг 4 (ИИ-валидация на антифрод)**

Помимо проверки на ПДн, ИИ-инспектор (Gemini API) осуществляет семантический скоринг полей `description` и `address_text` на предмет контентного фрода:

- **Скрытые контакты (Contact Bypass):** Обход ограничений (маски телефонов, Telegram, WhatsApp, «пишите в тг @username», «нол-семь-девять...»).
- **Фейковые цены (Price Baiting):** Несоответствие цены в реляционном ядре и в тексте (например, в БД указано 5 млн руб., а в описании: «первый взнос 5 млн, полная цена 15 млн»).
- **Чужой бренд (Duplicate Poaching):** Копирование объявлений конкурентов и призывы обращаться к сторонним лицам.

**Триггерная система санкций:** При фиксации фрода операция блокируется, объекту присваивается `status = 2` (Pending). Запись логируется в `agent_fraud_log`. При 3-м нарушении за 90 дней автоматически запускается триггер снижения рейтинга: `rating_penalty_points = 0.30`, `penalty_expires_at = NOW() + 90 дней`.

#### 5.1.5 Защита от «Галлюцинаций» ИИ при парсинге

Если ИИ-парсер не может достоверно извлечь цену (`price_cents`) или площадь (`floor_size`) с сайта застройщика/источника, **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** генерировать объект с фразой «Цена по запросу» или нулевыми значениями в реляционном ядре.

1. Объект автоматически переводится в статус Pending (код 2).
2. Устанавливается флаг `requires_manual_pricing = true` (новое поле в `properties`).
3. Запись помещается в очередь `moderation_queue` с приоритетом high.

**Эффект:** Исключает появление мусорных карточек в каталоге и галлюцинаций ИИ-Брокера (matcher) при семантическом сопоставлении.

**Шаг 5. Синхронизация и асинхронное обогащение**

Фоновый синхронизатор (Inngest) обрабатывает пачки валидных записей размером не более 100 записей.

**Схема обработки пачки:**

1. Каждая пачка валидируется повторно.
2. Валидные записи UPSERT-ятся в реляционное ядро с дедупликацией по физическому бизнес-ключу.
3. После успешного UPSERT объекту присваивается статус Enriching (код 6).
4. В очередь Inngest ставится задача на генерацию описания и инфраструктурного паспорта.
5. Задача выполняется асинхронно с экспоненциальными повторными попытками (до 3 раз).
6. В случае исчерпания попыток объект остаётся в статусе Enriching, а запись помещается в Dead-Letter Queue.

**Шаг 6. Публикация**

Администратор или агент проверяет объект и при необходимости переводит в `status = Active`.

**SEO-обогащение при публикации:**

После перевода объекта в Active, `ISlugGenerationService` автоматически:

1. Генерирует ЧПУ на основе нормализованного адреса.
2. Сохраняет маппинг в `property_seo_map`.
3. Формирует массив `location_geo_path` для построения хлебных крошек.
4. Инвалидирует кэш ссылок.

**Привилегированные взносы-ИИ-на возмещение затрат:**

- Рерайт описания под соцсети – 20 руб.
- Перевод на иностранные языки – 50 руб./язык.
- Расширенный SEO-текст – 100 руб.

#### 5.4.3 Автоматический «Зомби-аудит» (Data Decay Prevention)

В нише недвижимости до 30% объектов «протухают» ежемесячно. Для поддержания иллюзии «живого» рынка и повышения доверия ИИ-поисковиков внедряется автоматический аудит с настраиваемыми лимитами через `app_config`.

**Триггер:** Inngest workflow запускается ежедневно в 03:00.

**Настраиваемые лимиты (таблица `app_config`):**

- `zombie_audit_default_stale_days = 45` (по умолчанию для вторички)
- `zombie_audit_new_construction_stale_days = 30` (для новостроек — быстрее меняются)
- `zombie_audit_commercial_stale_days = 60` (для коммерции — длинный цикл)
- `zombie_audit_auction_stale_days = 7` (для гос-торгов — критичны сроки)
- `zombie_audit_dqs_penalty_percent = 15` (на сколько % снижать DQS)

**Логика:** Если объект в статусе Active не обновлялся агентом более лимита дней (определяется по `construction_status` и `usage_type`):

1. Data Quality Score объекта автоматически снижается на `zombie_audit_dqs_penalty_percent`.
2. Объект помечается флагом `is_stale = true`.
3. Объект исключается из топ-выдачи в каталоге и фидов (Google Merchant, Meta).

**Уведомление:** Агенту и руководителю агентства отправляется push/email: «Подтвердите актуальность N объектов, иначе они будут скрыты».

**Восстановление:** При любом действии агента (обновление цены, фото, подтверждение) флаг `is_stale` сбрасывается, и DQS восстанавливается.

**Эффект:** Создаёт поведенческий триггер для агентов заходить в систему, поддерживает свежесть базы и повышает доверие GEO.

**Seed для `app_config`:**

```sql
INSERT INTO app_config (key, value, description) VALUES
('zombie_audit_default_stale_days', '45', 'Лимит устаревания для вторички (дни)'),
('zombie_audit_new_construction_stale_days', '30', 'Лимит для новостроек'),
('zombie_audit_commercial_stale_days', '60', 'Лимит для коммерции'),
('zombie_audit_auction_stale_days', '7', 'Лимит для гос-торгов'),
('zombie_audit_dqs_penalty_percent', '15', 'Штраф DQS за устаревание (%)');
```

**Inngest Workflow: "Zombie Audit"**

- **Запуск:** `cron('0 3 * * *')`
- **Логика:**
  1. Читаем лимиты из `app_config`
  2. Для каждого `usage_type`/`construction_status` применяем свой лимит
  3. `UPDATE properties SET is_stale = TRUE, dqs = dqs * (1 - penalty/100) WHERE status = 1 AND last_confirmed_at < NOW() - INTERVAL '<N> days'`

## 6. МУЛЬТИКАНАЛЬНЫЙ ШАРИНГ И БЕСПЛАТНАЯ ДИСТРИБУЦИЯ (ФИДЫ САН)

### 6.1 Правила валидации объектов для экспорта

1. `status = 1` (Active).
2. Баланс агентства или привилегированного агента положительный.
3. Для Partner — разрешена автоматическая выгрузка объектов с `is_manual_override = false`. Для NonPartner — только если `is_manual_override = true` или используется покликовая оплата.
4. Статус объекта не должен быть ComingSoon (код 5).

### 6.2 Технический регламент Эксклюзивности (is_exclusive)

**Обнаружение дубля** – при попытке установки флага `is_exclusive = true` система выполняет поиск других объектов с тем же бизнес-ключом.

**Простые конфликты (автоматическое разрешение):**

- Если у существующего объекта `status = Archived` – флаг автоматически присваивается новому объекту.
- Если существующий объект не обновлялся более 90 дней – флаг переходит к новому объекту.

**Сложные конфликты (автоматическое разрешение по качеству):**

- Если оба объекта имеют статус Active, система сравнивает их Data Quality Score.
- Объект с более низким DQS автоматически переводится в статус Pending.
- Если DQS равны, создаётся запись в `exclusivity_disputes`, и обоим агентам отправляются уведомления с предложением инициировать процедуру через Арбитраж САН.

**Арбитраж САН** – процесс, в котором администратор выступает медиатором.

**Пошлина за Арбитраж:** 1 000 руб. с каждой стороны. В случае вынесения решения в пользу одной из сторон, пошлина проигравшей стороны не возвращается и направляется в фонд развития САН (30%) и победителю (70%).

**Санкции за фальсификацию документов:** Если обе стороны предоставили заведомо ложные документы, 100% внесённых пошлин направляются в фонд развития. Дополнительно рейтинг обоих агентов снижается на 0,5 балла сроком на 6 месяцев.

## 7. SEO, GEO, ЗАЩИТА ОТ КРАУЛЕРОВ И МИГРАЦИЯ

### 7.1 Архитектурный регламент SEO-индексации и Crawler Rate Limiting

1. **Изоляция краулингового бюджета:** Для ботов доступны только статические URL `/properties/[city]` и `/properties/[city]/[district]`.
2. **Фасетная отсечка:** Next.js Edge Middleware принудительно отдает `<meta name="robots" content="noindex, follow" />` для страниц с >2 динамическими фильтрами.
3. **Канонизация:** Пагинация (`?page=X`) снабжается тегом `<link rel="canonical" />` на корневую страницу.
4. **Circuit Breaker для ботов (Защита Supabase):** Если пул соединений Supabase ≥ 15, Middleware перехватывает запрос бота и отдает статическую HTML-копию из Next.js Data Cache или HTTP 429 (`Retry-After: 120`). Real-time пользователи получают прямой доступ к БД.
5. **Асинхронные фиды Sitemap.xml:** Генерация «на лету» запрещена. Внедряется `sitemap_index.xml` с сателлитными фидами (до 1000 объектов). Сборка переносится в Cron (Inngest) с 02:00 до 05:00.

#### 7.1.1 Регламент SSR и рендеринга

**Правило:** Все страницы каталога (`/properties/[city]`, `/properties/[id]`) рендерятся строго на сервере (SSR).

**Поведение:**

| Статус | HTTP-код | Действие |
|--------|----------|----------|
| ACTIVE | 200 OK | Полная карточка |
| SOLD_SOFT_404 | 200 OK | Маска деградации + блок AlternativeProperties |
| GONE_410 | 410 Gone | Уведомление + ссылки на похожие |
| NOT_FOUND | 404 | Стандартная 404-страница |

**Маска деградации (Soft-404):**

1. Плашка «Объект продан или снят с публикации».
2. Заблокированные CTA (телефон, заявка).
3. Блок «5 похожих квартир рядом» через `get_smart_alternatives()`.
4. `robots: { index: true, follow: true }` (сохраняем ссылочный вес).

#### 7.1.2 Регламент ЧПУ и редиректов

**Архитектурный паттерн генерации ЧПУ:**

1. В таблице `properties` НЕ хранится длинный slug (соблюдение лимита 200 байт).
2. ЧПУ хранится в таблице `property_seo_map` с внешним ключом `listing_key`.
3. Next.js Middleware выполняет 301-редирект: если запрос идёт по `listing_key`, он перенаправляется на красивый ЧПУ.
4. При изменении адреса объекта — старый slug сохраняется в таблице `seo_redirects_history` (TTL = 1 год) для сохранения ссылочного веса.

**Пример маршрутизации:**

```typescript
// Next.js Middleware
export async function middleware(request: NextRequest) {
  const slug = request.nextUrl.pathname.split('/').pop();
  if (slug?.startsWith('MLS-')) {
    const property = await slugService.resolveSlugToId(slug);
    if (property) {
      return NextResponse.redirect(
        new URL(property.full_slug, request.url),
        { status: 301 }
      );
    }
  }
  return NextResponse.next();
}
```

#### 7.1.3 Регламент Хлебных Крошек (Breadcrumbs)

**UI/UX (Mobile-First):**

- На экранах < 640px классические хлебные крошки ломают верстку.
- **Решение:** Горизонтальный скролл с градиентным затуханием справа (`overflow-x-auto` + CSS `mask-image: linear-gradient(to right, black 80%, transparent 100%)`) ИЛИ коллапсирующий вид: `[Воронеж] > [Центр] > ... > [Объект]`.

**SEO/GEO (JSON-LD):**

На каждой странице объекта (`/properties/[...]`) и странице аналитики/агента **ОБЯЗАТЕЛЕН** блок `BreadcrumbList`, построенный на основе иерархии `locations_geo`:

```json
{
  "@context": "https://schema.org",
  "@type": "BreadcrumbList",
  "itemListElement": [
    { "@type": "ListItem", "position": 1, "name": "Россия", "item": "https://san-portal.ru/ru" },
    { "@type": "ListItem", "position": 2, "name": "Воронеж", "item": "https://san-portal.ru/ru/voronezh" },
    { "@type": "ListItem", "position": 3, "name": "Центральный р-н", "item": "https://san-portal.ru/ru/voronezh/central" }
  ]
}
```

**Правила построения:**

- **Источник данных:** массив `location_geo_path` из `property_seo_map`.
- **Глубина:** от страны до района (максимум 5 уровней).
- **Локализация:** названия берутся из `locations_geo.display_name` с учётом locale.
- **Для международных объектов:** первый уровень — страна (`country_code`).

#### 7.2.2 Архитектура «Многоликой сущности» (Multi-Role Entity Pattern)

Одно физическое лицо представляется в системе как три отдельные сущности с разными ролями:

| Роль | URL | JSON-LD тип | Контент |
|------|-----|-------------|---------|
| Агент | can.blagorussia.ru/agents/[slug] | RealEstateAgent + Person | Объекты, сделки, отзывы |
| Автор-эксперт | obrazslov.ru/authors/[slug] | Person + Journalist / Analyst | Статьи, аналитика |
| Администратор | can.blagorussia.ru/staff/[slug] | Person + Employee | Новости платформы, changelog |

> **УТОЧНЕНИЕ:**
> В целях консолидации E-E-A-T (ссылочного веса и экспертного авторитета) роли «Исследователь», «Компилятор», «Редактор» и «Журналист» НЕ создаются как отдельные URL-сущности, а агрегируются внутри единой публичной персоны «Автор-эксперт» (`/authors/[slug]`).
>
> Различие между этими ролями осуществляется семантически, через массив `hasOccupation` в JSON-LD разметке (Person → hasOccupation → Occupation).
>
> Если роль «Редактор» или «Переводчик» принадлежит третьему лицу (например, античному автору или гостевому автору), это лицо фиксируется не через Multi-Role Entity, а через поля `contributor` / `source` в Тематическом паспорте и JSON-LD.

**Ролевые бейджи в UI:**

### 8.6 Механизм совместных сделок и распределения целевого вознаграждения

> **КРИТИЧЕСКОЕ ИСПРАВЛЕНИЕ:**
> Формула распределения вознаграждения изменена на **Принцип 50/50 + Корректировка**:
>
> - **Шаг 1. Базовое равенство:** Общая сумма делится поровну между всеми агентами-участниками (`S_base = S_total / N`).
> - **Шаг 2. Фиксированная корректировка (Разделы 1-4):** Применяются жесткие бонусы/штрафы за эксклюзивность, договор, показ, документы (от +/- 40%).
> - **Шаг 3. Плавающая величина «Оплата» (Раздел 5):** Выделяется пул в размере до 10% от общей суммы. Этот пул распределяется пропорционально реальным финансовым взносам клиентов каждого агента.
>
> `Итог_i = (S_total / N) + (S_total × %_fix / 100) + (S_total × 0.10 × Payment_i / ΣPayment)`

#### 8.6.1 Базовое правило

Общая сумма целевого вознаграждения по сделке распределяется между агентами по принципу 50/50, затем корректируется фиксированными процентами за вклад и плавающей величиной «Оплата» (до 10%), пропорциональной сумме, которую внёс клиент каждого агента.

**Принцип:** Базовое равенство + корректировка за вклад + пропорциональная оплата.

> **Важно:**
>
> - Сумма всех фиксированных процентов (как положительных, так и отрицательных) для одного агента не может превышать ±50% от общей суммы вознаграждения.
> - НЕТ автоматического пересчёта при превышении лимита. Если агент превысил лимит, он сам должен изменить значения в таблице (убрать какие-то действия).
> - Если итоговое целевое вознаграждение получается отрицательным, оно устанавливается в 0 руб., а нераспределённый остаток остаётся в системе и может быть распределён вручную администратором или через Арбитраж.

#### 8.6.2 Формула расчёта итогового целевого вознаграждения

```text
Базовая доля агента i = Общая сумма / N (где N — число агентов)

Итоговое целевое вознаграждение агента i =
  Базовая доля агента i +
  Σ(Фиксированные проценты за вклад агента i × Общая сумма / 100) -
  Σ(Фиксированные проценты за вклад ДРУГИХ агентов × Общая сумма / 100) +
  (Общая сумма × 0.10 × Сумма клиента агента i / Σ(Суммы клиентов всех агентов))
```

**Если сделка парсерная (`source_id > 0`):**

- Доля САН = Общая сумма × `san_platform_share_percent` (по умолчанию 5%)
- Сумма для распределения между агентами = Общая сумма - Доля САН

**Кто платит долю САН:**

- Если `agent.agency.agency_role = 1` (Partner) И `agent.pay_parser_fees_independently = false`:
  - payer = agent.agency (Агентство-партнёр)
  - Списание с баланса агентства → `target_fund = 2` (фонд инфраструктуры парсинга)
- Иначе (NonPartner, свободный агент, или `pay_parser_fees_independently = true`):
  - payer = agent (сам агент)
  - Списание с персонального баланса агента → `target_fund = 2`

**Если сделка НЕпарсерная (`is_manual_override = true`):**

- Доля САН = 0% (отчисления не производятся)
- Сумма для распределения между агентами = Общая сумма

**Параметры в `app_config`:**

| Параметр | Значение по умолчанию | Описание |
|----------|----------------------|----------|
| san_platform_share_percent | 5 | Доля САН в парсерных сделках (%) |
| san_platform_share_nonparser | 0 | Доля САН в непарсерных сделках (всегда 0) |

**Пример расчёта (парсерная сделка, 2 агента из разных агентств):**

- Общая сумма целевого вознаграждения: 200 000 руб.
- Базовая доля каждого агента: 100 000 руб. (50/50)
- Агент А работает в Агентстве-партнёре (`agency_role = 1`), `pay_parser_fees_independently = false`
- Агент Б работает в NonPartner-агентстве (`agency_role = 2`)

**Расчёт доли САН:**

- Доля САН: 200 000 × 5% = 10 000 руб.
- Сумма для распределения: 200 000 - 10 000 = 190 000 руб.

**Кто платит:**

- Агент А: его доля в распределении = 100 000 руб. → Агентство-партнёр платит 5 000 руб. (50% от 10 000 руб., пропорционально доле агента А)
- Агент Б: его доля в распределении = 100 000 руб. → сам агент Б платит 5 000 руб. (50% от 10 000 руб., пропорционально доле агента Б)

Далее 190 000 руб. распределяется между агентами по формуле из раздела 8.6.2.

**Юридический статус:**

- САН получает долю как оператор платформы (за инфраструктуру парсинга), а не как участник сделки.
- Администратор САН НЕ является третьим агентом и не подписывает акты приёма-передачи.
- Средства направляются в фонд инфраструктуры парсинга (раздел 3.3) на покрытие затрат: хостинг, API-сервисы, ИИ-генерация, модерация, хранение данных в MinIO.

**Отображение в калькуляторе (раздел 8.6.8):**

- Добавить строку "Доля платформы САН" в итоговый расчёт
- Показывать раздельно: "Целевое вознаграждение агента А / агента Б / платформы САН"
- Указывать, кто платит долю САН: "Агентство-партнёр [название]" или "Агент [ФИО]"
- Для Partner-агентов отображать: "Взнос покрыт агентством"
- Для NonPartner-агентов отображать: "Возмещение затрат на парсинг"

> **Примечание:** Размещение информации на сторонних площадках (Авито, ЦИАН, Яндекс.Недвижимость) НЕ включено в методику распределения целевого вознаграждения.

**Максимум в Разделе 4:** 3% (ипотека) + 2% (оценка) = **+5%** ✅

##### РАЗДЕЛ 5: ОПЛАТА (+10%)

| Критерий | Действие | Фиксированный процент | Подтверждение |
|----------|----------|----------------------|---------------|
| Сопровождение расчётов | Организация и контроль оплаты (Ваш) | от 0% до +10% от общей суммы | Акт приёма-передачи денег |
| | Не участвовал в оплате | 0% | — |

> **ВАЖНОЕ ПРИМЕЧАНИЕ:** Процент в разделе "Оплата" рассчитывается пропорционально в зависимости от доли платежа клиента агента относительно общего платежа по сделке.

**Примеры расчёта процента за оплату:**

- Если клиент агента заплатил 100% от общей суммы → агент получает +10%
- Если клиент агента заплатил 50% от общей суммы → агент получает +5%
- Если клиент агента заплатил 30% от общей суммы → агент получает +3%
- Если клиент агента не платил (оплата полностью от другого агента) → агент получает 0%

**Максимум в Разделе 5:** **+10%** ✅

#### 8.6.4 Примеры расчёта

**Пример 1: Стандартная совместная сделка (2 агента)**

- Общая сумма целевого вознаграждения: 150 000 руб.
- Клиент агента А заплатил: 100 000 руб. (66.67% от общей суммы)
- Клиент агента Б заплатил: 50 000 руб. (33.33% от общей суммы)

**ШАГ 1: Базовое распределение (50/50)**

- Базовая доля агента А = 150 000 / 2 = 75 000 руб.
- Базовая доля агента Б = 150 000 / 2 = 75 000 руб.

**ШАГ 2: Таблица процентов по разделам**

**Агент А:**

| № | Раздел | Критерии | Проценты |
|---|--------|----------|----------|
| 1 | ДОГОВОРНЫЕ ОТНОШЕНИЯ | Эксклюзивный договор (+8%) + Привлечение заявителя (+4%) + Переговоры (+8%) | +20% |
| 2 | РАБОТА С ОБЪЕКТОМ | Полное описание (+5%) + Организация показа (+5%) | +10% |
| 3 | ДОКУМЕНТАЛЬНОЕ СОПРОВОЖДЕНИЕ | Подготовка документов (+2%) + Проверка (+1%) + Регистрация (+2%) | +5% |
| 4 | ДОПОЛНИТЕЛЬНЫЙ ВКЛАД | Ипотечное содействие (+3%) | +3% |
| 5 | ОПЛАТА | (100 000 / 150 000) × 10% = 66.67% × 10% | +6.67% |
| | **ИТОГО процентов агента А** | | **+44.67%** |

**Агент Б:**

| № | Раздел | Критерии | Проценты |
|---|--------|----------|----------|
| 1 | ДОГОВОРНЫЕ ОТНОШЕНИЯ | Без договора (0%) | 0% |
| 2 | РАБОТА С ОБЪЕКТОМ | Краткое описание (+2%) + Сопровождение показа (+3%) | +5% |
| 3 | ДОКУМЕНТАЛЬНОЕ СОПРОВОЖДЕНИЕ | — | 0% |
| 4 | ДОПОЛНИТЕЛЬНЫЙ ВКЛАД | — | 0% |
| 5 | ОПЛАТА | (50 000 / 150 000) × 10% = 33.33% × 10% | +3.33% |
| | **ИТОГО процентов агента Б** | | **+8.33%** |

**ШАГ 3: Расчёт итогового целевого вознаграждения**

**Агент А:**

```text
Итоговое = Базовая доля + (Σ процентов агента А × Общая сумма / 100) - (Σ процентов агента Б × Общая сумма / 100)
= 75 000 + (44.67% × 150 000 / 100) - (8.33% × 150 000 / 100)
= 75 000 + 67 005 - 12 495
= 129 510 руб.
```

**Агент Б:**

```text
Итоговое = Базовая доля + (Σ процентов агента Б × Общая сумма / 100) - (Σ процентов агента А × Общая сумма / 100)
= 75 000 + (8.33% × 150 000 / 100) - (44.67% × 150 000 / 100)
= 75 000 + 12 495 - 67 005
= 20 490 руб.
```

**Проверка:** 129 510 + 20 490 = 150 000 руб. ✅

**Итог:** Агент А: 129 510 руб., Агент Б: 20 490 руб.

**Вывод:** Агент А получил больше, потому что внёс больший вклад в сделку (договор, переговоры, показ, документы, оплата), а также его клиент заплатил больше. Принцип «базовое равенство + корректировка за вклад + пропорциональная оплата» реализован корректно.

**Пример 2: Передача заявителя**

- Агент А передаёт заявителя Агенту Б
- Агент А получает: 10% от общей суммы целевого вознаграждения (за первичное привлечение)
- Агент Б получает: 90% от общей суммы целевого вознаграждения (за полную работу с заявителем)

**Пример 3: Передача объекта**

- Агент А передаёт объект Агенту Б
- Агент А получает: 15% от общей суммы целевого вознаграждения (за первичное привлечение объекта)
- Агент Б получает: 85% от общей суммы целевого вознаграждения (за полную работу с объектом)

#### 8.6.5 Механизм подтверждения вклада в сделку

**Фиксация вклада:** Каждое выполненное действие фиксируется в системе через:

- Загрузку документов (договоры, акты, скриншоты)
- Подпись заявителя (электронная или физическая)
- Подпись другого агента (взаимное подтверждение)
- Административное подтверждение (для спорных случаев)

**Сроки подачи:** Агент обязан зафиксировать свой вклад в течение 3 рабочих дней после совершения действия.

**Оспаривание:** Другой агент может оспорить фиксацию вклада в течение 5 рабочих дней через систему тикетов.

**Арбитраж:** Если агенты не достигли согласия, спор передаётся в Арбитраж САН (раздел 6.2). Пошлина за арбитраж — 1 000 руб. с каждой стороны.

#### 8.6.6 Передача заявителей и объектов

**Передача заявителя:**

1. Агент может передать заявителя другому агенту через систему (кнопка "Передать заявителя")
2. Заполняется акт приёма-передачи с указанием причины передачи
3. Новый агент получает 90% целевого вознаграждения за работу с заявителем
4. Старый агент получает 10% от целевого вознаграждения (за первичное привлечение)

**Передача объекта:**

1. Агент может передать объект другому агенту (например, при специализации)
2. Заполняется акт приёма-передачи с указанием причины
3. Новый агент получает 85% целевого вознаграждения за работу с объектом
4. Старый агент получает 15% от целевого вознаграждения (за первичное привлечение объекта)

**Документальное оформление:**

1. Все передачи фиксируются в таблице `client_transfers` и `property_transfers`
2. Указываются: дата, причина, старый агент, новый агент, условия целевого вознаграждения
3. Обе стороны подписывают акт (электронная подпись)

#### 8.6.7 Многосторонние сделки

**Цепочка сделок (альтернатива):**

- Если в сделке участвуют 3+ агента (например, альтернатива с 2 продавцами и 1 покупателем)
- Базовое распределение: поровну между всеми агентами (50/50/50...)
- Затем применяются корректировки по формуле из раздела 8.6.2
- При получении отрицательного целевого вознаграждения — оно устанавливается в 0, остаток не перераспределяется автоматически

**Несколько агентов с одной стороны:**

- Если одного заявителя представляют 2 агента, они делят свою долю 50/50 (или по договорённости)
- Договорённость фиксируется в системе через поле `internal_distribution_json`

#### 8.6.9 Порядок выплаты целевого вознаграждения

**Источник выплаты:**

- Целевое вознаграждение выплачивается заявителем (покупателем/арендатором) на основании договора
- Агенты получают целевое вознаграждение через систему САН или напрямую (по договорённости между участниками сделки)

**Сроки выплаты:**

- Агент обязан выплатить долю другому агенту в течение 5 рабочих дней после получения своего целевого вознаграждения
- Если выплата производится через систему САН — автоматическое распределение в течение 3 рабочих дней после подтверждения сделки

**Механизм распределения:**

- **Вариант А (через систему САН):** Агент загружает документы о сделке, система автоматически рассчитывает доли по формуле из раздела 8.6.2 и формирует платёжные поручения
- **Вариант Б (напрямую):** Агенты самостоятельно производят выплату друг другу на основании расчёта из калькулятора (раздел 8.6.8)

**Фиксация выплаты в системе:**

1. После выплаты агент загружает подтверждение (платёжное поручение, расписку)
2. Система фиксирует факт выплаты в таблице `commission_payments`
3. Оба агента получают уведомление о завершении расчёта

**Санкции за невыплату:**

Если агент не выплатил долю другому агенту в установленный срок:

1. Автоматическое уведомление администратору САН
2. Блокировка возможности участия в новых совместных сделках до погашения задолженности
3. Снижение рейтинга на 0,5 балла
4. При повторном нарушении — передача дела в Арбитраж САН

**Споры по выплате:**

- Если агент не согласен с суммой выплаты — он может оспорить расчёт через систему тикетов
- Срок рассмотрения спора: 5 рабочих дней
- При невозможности достижения согласия — передача в Арбитраж САН (раздел 6.2)

**Налоговые аспекты:**

- Все выплаты оформляются как добровольные целевые взносы в рамках некоммерческого сотрудничества
- Агенты самостоятельно несут ответственность за уплату налогов со своих доходов
- САН не является налоговым агентом и не удерживает НДФЛ

### 8.7 Механизм распределения входящих заявок на парсерные объекты (Lead Distribution)

**Цель:** Обеспечить автоматическое, справедливое и эффективное распределение клиентских запросов на объекты, не закреплённые ни за одним агентом. Распределение учитывает географическую близость агента к объекту как основной фактор, а рейтинг, нагрузку и специализацию – как корректирующие коэффициенты. Оповещение агентов происходит волнами (по 5–10 агентов за раз).

**А. Поступление заявки от клиента**

1. Клиент находит на сайте парсерный объект и заполняет форму.
2. Система проверяет, закреплён ли объект за агентом:
   - Если закреплён – заявка автоматически направляется этому агенту.
   - Если НЕ закреплён – заявка попадает в общий пул нераспределённых лидов (`pending_leads`) со статусом Pending.

**Б. Таблица нераспределённых лидов (pending_leads)**

```sql
CREATE TABLE pending_leads (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  client_request_id uuid REFERENCES client_requests(id),
  property_id uuid REFERENCES properties(id),
  status smallint DEFAULT 1, -- 1=Pending, 2=Offering, 3=Accepted, 4=Rejected, 5=Expired
  offered_to_agent_ids uuid[],
  current_batch integer DEFAULT 1,
  batch_size integer,
  accepted_by_agent_id uuid,
  candidates uuid[],
  created_at timestamp WITH TIME ZONE DEFAULT now(),
  updated_at timestamp WITH TIME ZONE DEFAULT now()
);
```

**В. Расчёт приоритетного скоринга агентов с использованием георасчёта**

**Оптимизация через PostGIS (фильтрация кандидатов):** Перед запуском сложного скоринга в Node.js, система выполняет SQL-запрос к PostGIS для отсечения заведомо неподходящих агентов. Запрос использует `ST_DWithin(agents.location, properties.geometry, lead_max_distance_km * 1000)` с GIST-индексом. В Node.js передаются только ID и базовые метрики агентов, попавших в гео-радиус (обычно не более 20–50 агентов), что снижает нагрузку на CPU и исключает задержки API. Параметр `lead_max_distance_km` в `app_config` определяет максимальное расстояние для включения агента в распределение.

Для каждого активного агента (`is_active = true`), прошедшего гео-фильтр, система рассчитывает приоритетный скор по формуле:

1. **Базовое значение** = Расстояние (км) от адреса агента до адреса объекта.
2. **Коэффициенты** (каждый в диапазоне 0.8–1.2):
   - **Рейтинг:** Коэф = 1.2 - (Rating / 25).
   - **Нагрузка:** Коэф = 1 + (Active_Load / 20).
   - **Специализация:** 0.9 (совпадение) или 1.1.
   - **Привилегированный агент / Партнёр:** 0.95.
3. **Итоговый скор** = Базовое значение × Коэф_рейтинга × Коэф_нагрузки × Коэф_специализации × Коэф_бонуса.

**Г. Волновое оповещение агентов**

1. Все активные агенты сортируются по возрастанию скора.
2. Система выбирает первые N агентов (N = `lead_batch_size`, по умолчанию 5).
3. В личном кабинете каждого из этих агентов появляется задача «Вам предложен лид» с таймером на ответ (по умолчанию 2 часа).

**Процесс принятия:**

1. Агенты нажимают кнопку «Принять».
2. По истечении времени система собирает всех кандидатов.
3. **Выбор финального владельца лида:**
   - **Автоматический** (`lead_selection_mode = 'auto'`): система выбирает агента с наилучшим совокупным скорингом.
   - **Ручной** (`lead_selection_mode = 'manual'`): администратор вручную выбирает агента.

**Если никто из волны не принял лид:**

1. Система расширяет круг: размер следующей волны удваивается.
2. Процесс повторяется до тех пор, пока лид не будет принят или не будут оповещены все активные агенты.
3. В последнем случае лид переходит в статус Expired.

Администратор может в любой момент переопределить распределение вручную.

**Д. Учёт статуса активности агента**

Агенты с `is_active = false` исключаются из всех волн.

**Е. Настройки администратора (в таблице `app_config`)**

| Параметр | Значение по умолчанию | Описание |
|----------|----------------------|----------|
| lead_batch_size | 5 | Количество агентов в первой волне |
| lead_response_timeout_hours | 2 | Время на ответ агента (в часах) |
| lead_max_distance_km | 50 | Максимальное расстояние от агента до объекта (км) |
| lead_coeff_rating | 0.04 | Коэффициент влияния рейтинга |
| lead_coeff_load | 0.05 | Коэффициент влияния нагрузки |
| lead_priority_partner | 0.95 | Бонусный коэффициент для партнёров |
| lead_selection_mode | 'auto' | Режим выбора: 'auto' или 'manual' |
| lead_min_candidates | 1 | Минимальное количество принявших |

## 9. МОДЕЛЬ УПРАВЛЕНИЯ, ЛИЦЕНЗИРОВАНИЕ И ВОЗМЕЩЕНИЕ ЗАТРАТ

### 9.1 Архитектурный Комитет САН

Для обеспечения долгосрочной устойчивости и демократичности, все стратегические изменения рассматриваются Архитектурным Комитетом.

**Состав комитета:**

- Представители агентств-партнёров (не более 5 человек).
- Представители привилегированных агентов (2 человека).

### 9.4 Интеграция с внешними партнёрами

#### 9.4.1 Модели доступа для внешних организаций

- **A.** API для массовых запросов (тарифы Free/Pro/Enterprise).
- **B.** Генерация индивидуальных отчётов для сделок — 500 руб. за отчёт (20% в центральный фонд, 80% — агенту).
- **C.** Подписка на обновления (Webhook / RESO EntityEvent).
- **D.** Инвестиционные и аналитические отчёты:
  - Инвестиционный паспорт района – от 3 000 руб.
  - Аналитический срез по объектам конкурентов – 5 000 руб.
  - Ежеквартальный отчёт по региону – от 50 000 руб.

#### 9.4.2 Техническая реализация

- Модуль `ExternalPartnerIntegrationService`.
- Авторизация через OAuth2.
- Rate limiting.
- Генерация PDF-отчётов с использованием Puppeteer.
- Все запросы логируются в `external_api_access_log`.

#### 9.4.3 Коммерческие условия и распределение доходов

Доходы распределяются: 70% – центральный фонд САН, 30% – резервный фонд.

Агенты, использующие сервис генерации отчётов, получают 80% от стоимости отчёта.

#### 9.4.4 Безопасность, конфиденциальность и механизм отзыва согласия

**Общие требования:**

- Передача данных осуществляется только по HTTPS с TLS 1.3.
- Доступ к ПДн строго запрещён.

**Отзыв согласия на передачу данных внешним партнёрам:**

**Инициатор – агент (без согласия клиента):**

1. Объект переводится в статус ComingSoon.
2. С баланса агента автоматически списывается административная комиссия (500 руб.).
3. Рейтинг агента снижается на 0,2 балла на срок 30 календарных дней.
4. Если в результате штрафа рейтинг привилегированного агента падает ниже 4,50, его статус и права в коллективных фондах продвижения замораживаются только со следующего расчётного периода.

**Инициатор – клиент (собственник):**

1. Клиент обращается к агенту.
2. Объект переводится в статус ComingSoon.
3. Рейтинг агента не снижается.
4. Для подтверждения волеизъявления клиента агент должен загрузить скан-копию заявления.

**Восстановление согласия:**

1. Агент или клиент может повторно дать согласие.
2. Объект автоматически возвращается во все внешние каналы.

**Логирование и аудит:**

- Все операции записываются в таблицу `consent_revocation_log`.
- Данные хранятся не менее 3 лет.

### 9.5 Уровни участия для агентств и агентов

## 10. ИНСТРУМЕНТЫ НАДЁЖНОСТИ, МОНИТОРИНГ И ОБРАБОТКА ОШИБОК

1. **Централизованное логирование** — все сервисы пишут логи в единую систему (Yandex Cloud Logging / ELK).
2. **Retry и Dead-Letter Queue** — для асинхронных задач используется Inngest с экспоненциальной задержкой.
3. **Мониторинг производительности** — через Prometheus + Grafana.

**Конкретные метрики:**

- Время выполнения SQL-запросов (p50, p95, p99).
- Использование CPU и RAM.
- Количество активных соединений к PostgreSQL.
- Задержки внешних API.
- Размер базы данных и отдельных таблиц.
- Количество ошибок валидации и синхронизации в ETL.
- Заполнение диска MinIO – алерт при 80%.
- Операции Cloudflare R2.
- Количество вызовов Yandex Cloud Functions – алерт при 800 тыс./мес.
- Время ответа MinIO – p95 < 200 мс.
- `infrastructure_enrichment_success_rate`.
- `infrastructure_enrichment_duration_p95`.
- Количество запросов к каждому внешнему API.
- Размер папки `infrastructure/` в MinIO.
- Целевые поступления от платных услуг.
- Использование heap-памяти Node.js – алерт при >80%.
- `video_publish_success_rate` — процент успешных публикаций видео на все платформы.
- `video_alternatives_db_coverage` — процент видео с заполненными альтернативами.
- `ai_bots_crawl_rate` — количество запросов от ИИ-ботов в сутки.
- `social_distribution_success_rate` — процент успешных публикаций в соцсети.
- `social_communities_paused_count` — количество сообществ в штрафной паузе.
- `social_suggestions_pending_count` — количество нерассмотренных предложений ИИ.
- `blogger_backup_success_rate` — успешность еженедельного бэкапа метаданных Blogger в Git.
- `status_md_autoupdate_success_rate` — успешность авто-обновления STATUS.md.
- `migration_static_to_nextjs_progress` — прогресс замещения статической версии на Next.js (цель: 100% через 90 дней).
- `gallery_export_success_rate` — успешность экспорта изображений в gallery.obrazslov.ru.

## 13. РЕГЛАМЕНТ ИНТЕГРАЦИИ МИРОВЫХ ПРАКТИК MLS В СИСТЕМУ САН

### 13.1 Внедрение стандарта RESO (Real Estate Standards Organization)

В США обмен данными между всеми агентствами, банками и застройщиками стандартизирован через Data Dictionary ассоциации RESO.

**Единый словарь данных (Data Dictionary):** Структура таблиц `properties` в Supabase САН должна строго наследоваться от полей RESO. Например, вместо хаотичных названий полей используются детерминированные типы: `LivingArea` (вместо `square_meters`), `BathroomsTotal`, `HeatingType` (с кодированием через smallint).

**Унификация API:** Интеграционный слой САН на Этапе 1 должен поддерживать спецификацию RESO Web API (на базе OData). Это позволит крупным агентствам недвижимости мгновенно подключать свои внутренние CRM-системы (Битрикс24, amoCRM) к САН по общемировому стандарту без написания кастомных парсеров.

### 13.2 Стратегия сертификации RESO

**Целевой сертификат:** RESO Web API Server & Data Dictionary Certification (Level 1)

Это «Золотой стандарт» для MLS-систем, который позволяет САН легитимно интегрироваться с любыми мировыми CRM (Salesforce, HubSpot, amoCRM, Битрикс24) и зарубежными порталами без написания кастомных парсеров.

**Бизнес-ценность:**

- **B2B Экспансия:** Любое крупное агентство или застройщик сможет подключить свою CRM к САН за 15 минут, используя стандартный RESO-коннектор.
- **Международный рынок:** При выходе в страны СНГ, ОАЭ или Европу не придётся переписывать ядро. Мы просто добавим Локальный Адаптер, а ядро останется в стандарте RESO DD.
- **GEO и ИИ-поиск:** ИИ-роботы (Perplexity, Bing) «обучены» на данных RESO. Если наш JSON-LD и API отдают данные в форматах RESO, доверие (Trust Rank) к САН со стороны LLM возрастает кратно.

**Дорожная карта получения сертификата:**

- **Этап 0 (Текущий):** Внутренняя архитектура полностью готова. Данные хранятся в оптимизированном виде.
- **Этап 1 (Пилот B2B):** Внедрение `IRESODataMapper`. Публичный API начинает отдавать данные в формате RESO DD. Подача заявки на RESO Data Dictionary Compliance (Self-Assessment).
- **Этап 2 (Масштабирование):** Прохождение официального аудита RESO. Получение бейджа RESO Certified Web API Server. Интеграция с международными порталами (Zillow, Rightmove) через стандартные RESO-коннекторы.

**Архитектурный слой RESO-адаптации:**

Внутренняя оптимизация БД (правило 200 байт, smallint) сохраняется. На уровне API работает `IRESODataMapper`, который переводит:

- `construction_status = 1` (smallint) → `ConstructionStatus = 'NewConstruction'` (строка RESO)
- `price_cents = 850000000` (bigint) → `ListPrice = 8500000`, `ListPriceCurrencyCode = 'RUB'`

### 13.3 Протокол гарантированного разделения целевого вознаграждения (Cooperative Compensation)

Фундамент классической американской MLS — юридическое обязательство листинг-агента (агента собственника) разделить целевое вознаграждение с кооперирующим агентом (агентом покупателя), который привел клиента.

**Поля в БД:** В таблицу `properties` добавляются обязательные B2B-поля: `buyer_agent_compensation` (процент или фиксированная сумма целевого вознаграждения для коллеги) и `compensation_type_code` (1 = Percent, 2 = Fixed).

**Меритократический контроль:** Информация о целевом вознаграждении скрыта от B2C-пользователей, но видна агентам в личном кабинете. Если агент отказывается выплатить зафиксированную в САН долю целевого вознаграждения после сделки, пострадавшая сторона подает заявку в Арбитраж САН. Факт уклонения влечет обнуление меритократического рейтинга агента (`rating = 0`) и пожизненный бан его агентства в системе.

### 13.4 Статус-код система жизненного цикла объекта (MLS Statuses)

Мировые MLS не используют бинарную логику «активно / продано». Внедряется детальная система статусов (`property_status_code`), которая управляет видимостью для SEO, ИИ-роботов и внутренних агентов:

- **Active (ACT):** Объект открыт для показов, индексируется SEO и ИИ.
- **Under Contract / Pending (PEND):** За объект внесен задаток, идет проверка документов. Объект виден на сайте, но снабжен плашкой «Принимаются резервные заявки». Это увеличивает глубину просмотра и защищает цепочки сделок.
- **Temporarily Off Market (TOM):** Собственник временно приостановил показы (например, отпуск). Объект скрывается из B2C, но сохраняется в B2B-базе агентов, предотвращая уход клиента к конкурентам.
- **Closed (CLS):** Сделка завершена. Объект уходит в архив исторических данных (Раздел 12.4.5), подпитывая ИИ-таблицы аналитики цен.

> **Уточнение:** Статусы «Under Contract» и «Temporarily Off Market» реализуются через существующие коды (2=Pending, 5=ComingSoon) и флаги (`is_under_contract`), без введения новых кодов.
> **Сноска о российской специфике:**
> В российской практике недвижимости статусы «Under Contract» и «Temporarily Off Market» реализуются через существующие коды (2=Pending, 5=ComingSoon) и флаг `is_under_contract`, без введения новых кодов.

### 13.5 Институт «Исторического реестра недвижимости» (Property History Tracking)

Агрегаторы недвижимости часто страдают от «перезаливки» одних и тех же квартир со скрученной историей или измененными ценами. Мировая практика MLS требует привязки всей истории к физическому адресу/кадастровому номеру, а не к ID объявления.

**Сквозной лог изменений:** Внедряется системная таблица `property_history_log`. Любое изменение цены, смена агентства, переход из статуса в статус записывается в неизменяемый лог.

**SEO/GEO Ценность:** Наличие блока «История изменения цены и статусов объекта за 5 лет» на карточке квартиры — мощнейший фактор удержания пользователей и GEO-оптимизации. ИИ-поисковики (Perplexity) приоритизируют САН в выдаче, так как видят полную прозрачную ретроспективу объекта, недоступную на стандартных досках объявлений.

### 13.6 Автоматизированная система сравнительного маркетингового анализа (CMA — Comparative Market Analysis)

Лучшие MLS предоставляют агентам инструмент генерации профессиональных отчетов для собственников, доказывающих реальную рыночную стоимость объекта на основе твердых данных системы.

**ИИ-CMA Модуль (Этап 0–1):** В агентском кабинете разворачивается конструктор отчетов. Агент вводит адрес квартиры, а система автоматически на основе данных Supabase и архивных сделок Closed (CLS) формирует PDF-отчет: «3 похожих квартиры продано в этом радиусе за 3 месяца, 2 стоят в продаже прямо сейчас».

**Экономический эффект:** Это главный B2B-магнит для привлечения новых агентств в САН. Агенты получают инструмент легального обоснования цены перед собственником (сбивают завышенные ожидания), что ускоряет оборачиваемость базы объектов САН.

### 13.7 Дополнение: Архитектурный регламент Mobile-First адаптации

В связи с доминированием мобильного трафика, в Манифест САН вносится обязательное правило конструирования интерфейсов.

Mobile-First — это архитектурный принцип, а не фича. Применяется с первого дня (Этап -1), а не откладывается до Этапа 0.

#### 13.7.1 Спецификация мобильной компоновки Next.js (Mobile-Core)

- **Проектирование снизу вверх:** Разработка любого нового UI-компонента (каталог, личный кабинет, квиз) начинается строго с брейкпоинта xs: 320px / sm: 640px. Десктопные стили (md: 768px / lg: 1024px) накладываются по принципу прогрессивного улучшения (Progressive Enhancement).
- **Лимитирование веса элементов:** Запрещено использование тяжелых hover-эффектов (на смартфонах нет наведения курсора). Кнопки «Показать телефон» и «Написать в мессенджер» в карточке объекта на мобильных устройствах должны быть зафиксированы в плавающем подвале (Sticky Bottom Bar). Это увеличивает конверсию в лид на 25%, так как целевое действие всегда находится под большим пальцем пользователя.
- **Оптимизация фасетных фильтров:** На экранах смартфонов блок из 50 фильтров убирается в полноэкранное модальное окно (Drawer), открывающееся по кнопке «Фильтры». Внутри Drawer обязателен липкий подвал с динамическим счетчиком: `[Показать 1 240 объектов]`, который обновляется без перезагрузки через API при каждом изменении параметров.

## 14. СТРАТЕГИЧЕСКИЕ ИНЖЕНЕРНЫЕ РЕКОМЕНДАЦИИ ПО РЕАЛИЗАЦИИ САН

### 14.1 Регламент верификации дублей по Кадастровым номерам (Data Integrity)

В нише недвижимости агрегаторы часто забиты дубликатами — одно и то же объявление выставляют 5 разных агентов с разной ценой. Это уничтожает доверие пользователей и ИИ-моделей.

**Кадастровый ID как неизменяемый ключ:** Начиная с Этапа 0, в реляционное ядро вводится поле `cadastral_number varchar(30) NULL`.

**Логика сквозной склейки:** Если при парсинге или ручном вводе обнаруживается совпадение кадастрового номера, система блокирует создание новой карточки. Вместо этого включается логика «Мульти-листинга»: создается одна базовая гео-сущность объекта недвижимости, внутри которой авторизованные агенты могут конкурировать условиями сделки или размером своей доли целевого вознаграждения (в B2B контуре). Это очистит выдачу и поднимет авторитетность сайта для GEO (AI SEO).

### 14.2 Архитектура шифрования ПДн на уровне БД (Соответствие 152-ФЗ в Supabase)

Бесплатный тариф Supabase Cloud Free является облачным решением хостинга, расположенным за пределами РФ. Прямое хранение персональных данных (ФИО, телефоны, паспорта агентов/собственников) в открытом виде нарушает закон 152-ФЗ.

**Запрет на открытый текст:** Запрещено хранить номера телефонов клиентов и собственников в незашифрованном виде в таблицах базы данных.

**Паттерн Crypto-Hash Шлюза:** В схему БД внедряется хранение только `phone_hash varchar(64)` (SHA-256 с солью) для поиска совпадений. Сам номер телефона шифруется на сервере sGTM / Yandex Cloud Functions с помощью симметричного алгоритма AES-256 с использованием закрытого ключа, хранящегося в защищенных переменных окружения (.env) российской инфраструктуры, и пишется в БД как `phone_encrypted bytea`. При парсинге или утечке БД злоумышленники увидят только массив случайных символов.

### 14.3 Замена классической пагинации на гибридный Infinite Scroll

Стандартная постраничная навигация (1, 2, 3... 99) неудобна на мобильных устройствах (Mobile-First), а бесконечная прокрутка (Infinite Scroll) «топит» краулинговый бюджет, так как поисковые роботы не умеют прокручивать экран для подгрузки данных.

**Архитектурный компромисс:** Для листингов САН внедряется гибридный скролл с кнопкой. Первые 20 объектов рендерятся строго на сервере (SSR) для роботов и ИИ. Внизу страницы размещается кнопка `[Показать еще 20 объектов]`, которая для обычных пользователей подгружает контент асинхронно через API без перезагрузки, а для поисковых ботов является стандартной ссылкой `href="/properties/voronezh?page=2"`.

**Эффект:** Идеальная глубина индексации роботами + максимальное удержание пользователей на смартфонах.

### 14.4 Контур «Партизанского» B2B-маркетинга на Этапе -1 (Лидогенерация франшизы)

Для удержания 1–2 пилотных агентств и подготовки почвы для масштабирования на Этапе 0, ИТ-платформа даёт им мгновенную ценность через инструмент "Проверка объекта на фрод". После 3 бесплатных проверок система просит агента: "Для продолжения авторизуйтесь как Агентство недвижимости САН". Это обеспечит органический прирост B2B-базы после успешной валидации ядра на пилотных агентствах.

## 15. РЕГЛАМЕНТ УПРАВЛЕНИЯ ИИ-КОНТЕКСТОМ И ВЕКТОРИЗАЦИИ (VECTOR ARCHITECTURE)

### 15.1 Отказ от pgvector на Этапе 0

**ЗАПРЕЩЕНО** использование расширения `pgvector` в Supabase на Этапе 0.

**Обоснование:** 50 000 векторов × 6 КБ = 300 МБ (60% лимита Supabase 500 МБ). Это мгновенно исчерпает бесплатный тариф.

**Альтернатива:** Семантический поиск через `smallint[]` теги-синонимы (см. Раздел 17.3).

#### 15.1.3 Адаптер Векторизации

Хотя на Этапе 0 используется `smallint[]` (§17.3), при росте базы до 50 000+ объектов поиск по пересечению массивов (`&&`) начнёт деградировать.

Заранее проектируется интерфейс `IVectorSearchService`.

- **Реализация Этапа 0:** `SmallintArraySearchAdapter` (текущая логика).
- **Реализация Этапа 1:** `QdrantAdapter` (Qdrant развёрнут в том же Docker-контейнере, что и MinIO) или `YandexSearchServiceAdapter`.

**Эффект:** Бесшовная миграция с `smallint[]` на полноценный векторный поиск без переписывания бизнес-логики Next.js.

### 15.2 Архитектурный паттерн конструирования ИИ-паспорта (Context Builder)

Чтобы векторный поиск работал корректно, эмбеддинг должен генерироваться не по хаотичному тексту агента, а по строго детерминированному ИИ-паспорту объекта.

При UPSERT операции бэкенд Next.js автоматически собирает плоскую текстовую строку (контекст) по следующему шаблону:

```text
Объект: {property_type}. Статус: {status_code}. Город: {city}, Район: {district}, Адрес: {address_text}.
Параметры: Комнат: {rooms}, Площадь: {floor_size} кв.м., Этаж: {floor}/{max_floor}. Цена: {price} рублей.
Инфраструктура (ИИ-теги): {infrastructure_tags_array}.
Описание агента: {description}.
```

Эта строка отправляется на API векторизации, и полученный массив чисел записывается в `property_vector`. Это гарантирует, что ИИ-поисковики всегда будут выдавать релевантные ответы.

**Ролевая фильтрация в RAG-контексте:**

При формировании ИИ-паспорта объекта для RAG-контекста, в системный промпт для внешних LLM обязательно передаётся информация о роли:

```text
КОНТЕКСТ АВТОРА:
Роль: [agent | author | staff]
Имя: [Имя]
Рейтинг: [X] (если agent)
Специализация: [список]
Раскрытие интересов: [да/нет]
```

**Эффект:** ИИ-Брокер (matcher) и ИИ-аналитик (analyst) корректно фильтруют контекст и не смешивают роли.

### 15.3 Защита от «галлюцинаций» ИИ через RAG (Retrieval-Augmented Generation)

При вызове API САН через внешние плагины существует риск, что модель ChatGPT или Клод «придумает» несуществующие параметры объекта или перепутает цену.

**Архитектурный запрет:** Запрещено передавать текстовое описание объекта напрямую в LLM без жестких ограничений. Интеграционный слой AI-Gateway обязан использовать паттерн RAG:

1. Система извлекает строгие факты из JSON-паспорта (цена, площадь, статус).
2. Формирует системный промпт (System Prompt) для внешней модели:

```text
Вы — ИИ-ассистент платформы САН. Отвечайте пользователю строго на основе предоставленных данных.
Если данных нет в блоке "Факты", ответьте "Данные отсутствуют". Вам запрещено выдумывать параметры.

ФАКТЫ ОБЪЕКТА: Цена {price}, Комнат {rooms}, Ссылка {url}.
```

Это полностью исключает дезинформацию клиентов и защищает репутацию бренда САН.

## 17. СЕМАНТИЧЕСКАЯ АРХИТЕКТУРА (БЕЗ PGVECTOR)

> Альтернатива pgvector. **Обоснование:** 50 000 векторов × 6 КБ = 300 МБ (60% лимита).

### 17.1 Архитектурный паттерн ИИ-паспорта (Context Builder)

Каждый объект недвижимости имеет «ИИ-паспорт» — структурированный JSON, собираемый из:

- Таблицы `properties` (цена, площадь, комнаты, район).
- Таблицы `system_enums` (теги-синонимы).
- ИИ-описания (прошедшие Лингвистический шлюз, п. 5.1.6).
- Агрегированных отзывов района.

### 17.2 Защита от галлюцинаций через RAG

ИИ-агент получает только данные из ИИ-паспорта. Запрет на генерацию фактов, отсутствующих в БД.

**Правило промпта:** «Используй ТОЛЬКО данные из контекста. Если данных недостаточно — ответь "Нет данных в базе".»

### 17.3 Семантический поиск через smallint[] теги

**Схема:**

```sql
-- Таблица тегов-синонимов
CREATE TABLE semantic_tags (
  id SMALLINT PRIMARY KEY,
  label VARCHAR(50) NOT NULL,
  synonyms TEXT[] NOT NULL,     -- ['светлая', 'солнечная', 'южная сторона']
  category VARCHAR(30) NOT NULL -- 'lighting', 'infrastructure', 'family'
);

-- Поле в properties
ALTER TABLE properties ADD COLUMN semantic_tags SMALLINT[] DEFAULT '{}';
CREATE INDEX idx_properties_tags ON properties USING GIN (semantic_tags);
```

**Запрос:**

```sql
-- «Светлая квартира рядом со школой» → теги [12, 45]
SELECT * FROM properties
WHERE semantic_tags && ARRAY[12, 45]::smallint[]
ORDER BY array_length(semantic_tags & ARRAY[12, 45]::smallint[], 1) DESC;
```

**Объём данных:** 50 000 объектов × 10 тегов × 2 байта = ~1 МБ (vs. 300 МБ для pgvector).

## 19. ИНТЕГРАЦИЯ С ИНФРАСТРУКТУРОЙ ЭКОСИСТЕМЫ (@blago-nko и @can-secure-dev)

Платформа САН разрабатывается под аккаунтом `can-secure-dev` (см. п. 1.3.5), общие артефакты экосистемы — под `@blago-nko`. Настоящий раздел развивает САМ § 3.3 и фиксирует технические механизмы единообразия между организациями.

### 19.1. Общие артефакты (GitHub Packages)

- Репозиторий `blago-nko/shared-assets` (см. Глоссарий: Shared Assets) публикует общие компоненты в приватный npm-реестр GitHub Packages.
- Платформа САН подключает их как зависимости через `package.json`.

Конфигурация `.npmrc`:

```ini
@blago-nko:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${BLAGO_NPM_TOKEN}
```

- Токен `BLAGO_NPM_TOKEN` хранится в GitHub Secrets организации @can-secure-dev; ротация — по САМ § 3.3.4.
- Версионирование — SemVer; breaking changes — только через протокол `MIG-`.
- Fork-версии shared-assets запрещены.
- Обновление версий контролируется Renovate Bot с автоматическим PR и запуском `architecture-check`.

### 19.2. Единый CI/CD-контур (Reusable Workflows)

Общие workflows размещаются в уже существующем каталоге `blago-nko/.github/workflows/` и расширяют его:

| Workflow | Назначение |
| --- | --- |
| `architecture-check.yml` | Валидация кода на соответствие САМ и настоящему манифесту |
| `protocol-check.yml` | Проверка префиксов PR (`SAM-`, `SAN-`, `MIG-`...) и ссылки на утверждённый протокол (раздел 12) |
| `sync-manifests.yml` | Рассылка обновлений манифестов в зависимые репозитории |
| `publish-assets.yml` | Публикация shared-assets в GitHub Packages |
| `ai-rules-sync.yml` | Обновление `.cursorrules` / `.github/copilot-instructions.md` из разделов 12 и 15 |

Каждый PR в @can-secure-dev проходит обязательные этапы (Required Status Checks):

| Этап | Проверяет | Блокирует мерж |
| --- | --- | --- |
| `architecture-check` | САМ + настоящий манифест | ✅ |
| `protocol-check` | Префикс и ссылка на протокол (раздел 12) | ✅ |
| `unit-tests` | Модульные тесты | ✅ |
| `reso-validation` | Соответствие RESO Data Dictionary (разделы 13, 18.4) | ✅ |
| `security-scan` | Выполнение требований 152-ФЗ (разделы 14.2, 1.3.5) | ✅ |

### 19.3. GitHub App и Branch Protection

- Кросс-организационный контроль выполняет GitHub App `Blago Ecosystem Bot` (`contents:read`, `checks:write`, `pull_requests:write`, `issues:read`), установленный в обеих организациях.
- Логика: failure любого этапа из п. 19.2 → label `🚫 протокол нарушен`; отсутствие префикса → label `⚠️ нет префикса`; мерж блокируется.
- Ветка `main` в @can-secure-dev: минимум 1 approve от Архитектурного комитета; все статусы п. 19.2 — success; запрет force-push; linear history.

### 19.4. Feature flags

- Единый источник значений флагов САН — `manifests/feature-flags/san.json`.
- Руководство по использованию флагов остаётся в `/docs/feature-flags.md` (п. 11.10).
- При обновлении значений `sync-manifests.yml` создаёт PR `[AUTO-SYNC]` в @can-secure-dev; до мержа новые флаги неактивны (fail-safe).

### 19.5. Синхронизация инструкций для ИИ-агентов

- Настоящий раздел не дублирует правила разделов 12 и 15, а фиксирует механизм их доставки: `ai-rules-sync.yml` при каждом обновлении разделов 12/15 обновляет `.cursorrules` / `.github/copilot-instructions.md` во всех репозиториях экосистемы.
- ИИ-агент, обнаружив необходимость архитектурного изменения, действует строго по разделу 12: останавливает генерацию и выводит блок:

```text
⚠️ ПРЕДЛОЖЕНИЕ ПО ИЗМЕНЕНИЮ МАНИФЕСТА
Префикс: SAN-XXX
Описание: [суть изменения]
Затронутые разделы: [номера разделов]
Обоснование: [почему текущий манифест не покрывает задачу]
```

### 19.6. Мониторинг

- Отдельный отчётный файл НЕ создаётся: инфраструктурные метрики (число заблокированных PR, версии shared-assets в проектах, дата последней синхронизации манифестов) добавляются новым блоком в существующий реестр `STATUS.md` (см. Глоссарий).
- Генератор блока — расширение существующего `scripts/update_status.py`.
