## 📋 ВВЕДЕНИЕ

Настоящий документ является сквозным техническим руководством для миграции 14 доменов экосистемы. Миграция выполняется в **три этапа**:

- **Этап 1 (Быстрый переезд):** Все 14 сайтов переносятся на новую инфраструктуру в их текущем виде — 11 RSS-сайтов как статические, `grekpanteon.obrazslov.ru` как статический дамп, `can.blagorussia.ru` — временная статическая landing-заглушка на Hugo (до готовности Next.js MVP), `gallery.obrazslov.ru` — на Blogger с кастомным доменом.
- **Этап 2 (MVP и замещение на целевые движки):** После успешного переезда всей экосистемы, `grekpanteon.obrazslov.ru` постепенно замещается на полноценную версию на Astro + Yandex Object Storage (16 505+ страниц, ИИ-конвейер), а `can.blagorussia.ru` — на платформу САН на Next.js с Supabase и всеми сервисами.
- **Этап 3 (Масштабирование):** Масштабирование инфраструктуры, подключение промышленных БД, B2B-интеграции, RESO-сертификация.

### Матрица соответствия этапов (Stage Mapping)

Физический перенос инфраструктуры (Миграция) предшествует логическому развитию продукта (Архитектура САН/САМ).

| Миграционный Этап (МИГРАЦИЯ) | Архитектурный Этап (САМ / САН) | Суть состояния |
| :--- | :--- | :--- |
| Миграционный Этап 1 | Предшествует (Baseline / Legacy) | Физический перенос текущих данных и статических дампов на новую инфраструктуру (GitHub Pages). Продукт еще не развивается. |
| Миграционный Этап 2 | Архитектурный Этап -1 | Развертывание каркаса (Next.js/Vercel). Начало активного развития MVP САН на новом стеке. |
| Миграционный Этап 3 | Архитектурные Этапы 0 и 1 | Масштабирование, подключение БД, B2B-интеграции, RESO-сертификация. |

Архитектура и детали переноса для `grekpanteon.obrazslov.ru` описаны в отдельном Манифесте Грек-Пантеон, а для САН — в Манифесте САН. Настоящий манифест фокусируется на RSS-сайтах, общей инфраструктуре (DNS, хостинг, мониторинг, WAF, Image Sanitization, Blogger-витрина), SEO-преемственности и координации запуска с платформой САН и Пантеоном.

**Перечень сайтов, описываемых в данном манифесте:**

- Основные порталы `blagorussia.ru` и `obrazslov.ru`;
- Центральный хаб `partnerstvo.blagorussia.ru` с виджетом обратной связи;
- Остальные тематические поддомены: `obavlenia.blagorussia.ru`, `interesnye-mesta.obrazslov.ru`, `ot-gorozan.blagorussia.ru`, `novosti.blagorussia.ru`, `moisites.blagorussia.ru`, `joga.blagorussia.ru`, `ideologia.obrazslov.ru`, `nasa-istoria.blagorussia.ru`;

Сайт `grekpanteon.obrazslov.ru` (16 505+ страниц) описывается в отдельном Манифесте Грек-Пантеон. Его миграция выполняется синхронно с остальными доменами.

## ВВЕДЕНИЕ (АРХИТЕКТУРНЫЕ ПРИНЦИПЫ)

Настоящий документ описывает полный цикл переноса 14 сайтов экосистемы (11 RSS + САН + Пантеон + gallery), но с разделением ответственности: RSS-сайты и общие сервисы – в данном манифесте, САН и Пантеон – в их собственных манифестах.

Специфические принципы, применяемые к RSS-сайтам и платформе САН (общие принципы см. в САМ, раздел 1.3 и Приложение А):

- **GEO-оптимизация** – Тематический паспорт, Трёхуровневый Граф Знаний, JSON-LD разметка, Identity Graph.
- **E-E-A-T** – Архитектура «Хаб и Спицы», двойная атрибуция, ручная корректировка ролей, раскрытие конфликта интересов.
- **Mobile-First** – xs:320px, Sticky Bottom Bar, Mobile-First хлебные крошки.
- **Видео-инфраструктура** – отказ от R2, мульти-загрузка на внешние платформы, Видео-Матрица РФ, двойное зеркалирование, Единый Видео-Реестр.
- **Защита от ИИ-краулеров** – WAF для GPTBot, ClaudeBot, PerplexityBot, YandexAdditional.
- **Социальные ссылки** – централизованный конфиг по брендам, динамические кнопки действий.
- **Аудит битых ссылок** – трёхэтапная проверка с генерацией отчёта.
- **Семантические URL** – новые ЧПУ с 301-редиректами, паттерн Book/Chapter.
- **Image Sanitization Pipeline** – обработка изображений выполняется согласно САМ (п. 2.5).
- **Регистрация в поисковых системах** – выполняется согласно САМ (п. 7.2.7).
- **Атрибуция изображений** – выполняется согласно САМ (п. 2.5 и 7.2.4).
- **Поэтапная публикация** – суточный лимит 200 страниц, подэтапы по батчингу ID (5000 URL/файл) для sitemap.
- **Эволюционная модель хранения медиа** – выполняется согласно САМ (п. 2.4).
- **Единый стандарт фронтенда** – все сайты используют shared-assets (САМ п. 1.6).
- **Политика конфиденциальности** – размещается на всех 14 сайтах (САМ Приложение Г).

Инструменты разработки соответствуют единому стандарту, описанному в САМ (п. 1.4). Все компоненты экосистемы используют Open Source решения согласно этому стандарту. Подробное руководство: `/docs/DEVELOPMENT_TOOLS.md`.

#### 5.1.3. Статический дамп grekpanteon.obrazslov.ru (№4)

На первом этапе `grekpanteon.obrazslov.ru` мигрируется как статический дамп:

1. Из текущего источника данных (Google Таблицы) генерируются статические HTML-страницы для **~300 готовых статей (ядро контента)** с использованием **Hugo** в режиме статической генерации (без ИИ-конвейера).
2. Все изображения проходят Image Sanitization Pipeline (согласно САМ п. 2.5) и загружаются в Blogger (основное хранилище).
3. Генерируются sitemap-файлы по принципу батчинга по ID (5000 URL/файл).
4. Сайт разворачивается на GitHub Pages с сохранением всех существующих URL (slug).
5. Настройка DNS: `grekpanteon.obrazslov.ru` → CNAME на GitHub Pages.

На этом этапе сайт работает как статический архив контента, доступный для пользователей и поисковых систем.

**Ограничения Этапа 1:**

- ❌ Отсутствует ИИ-конвейер генерации описаний
- ❌ Отсутствуют причинно-следственные связи
- ❌ Отсутствует геоинформационный слой
- ❌ Отсутствует интерактивность (комментарии, поиск, фильтрация)

**Целевой стек хранения данных для Этапа 2:** Parquet-файлы в Yandex Object Storage + обработка через DuckDB.

#### 5.1.4. Стратегия миграции САН (Упрощенный транзит) (№13)

**Миграционный Этап 1 (Статический архив):**

Старая версия платформы САН (30 страниц) выгружается в статический HTML-дамп и деплоится на **Vercel (аккаунт `can-secure-dev`)** для сохранения изоляции ПДн-контура. **Миграционный Этап 2 (Переезд на промышленный стек):**

Старый статический дамп на GitHub Pages удаляется.

**Соответствие 152-ФЗ (сохраняется):**

Vercel используется исключительно для рендеринга UI и SSR. Весь конвейер ПДн проходит через российский ПДн-шлюз на Yandex Cloud Functions (шифрование AES-256-GCM до передачи в Supabase). Аккаунт зарегистрирован на международный Google-аккаунт для доступа к Gemini API. Подробнее о структуре аккаунтов см. Приложение В САМ.

## 7.1.9. Расширенная семантическая разметка для ИИ-поисковиков (GEO)

Для всех 14 сайтов экосистемы обязательна следующая расширенная семантическая разметка:

**JSON-LD BreadcrumbList:**

- На всех страницах (кроме главной) обязательна разметка хлебных крошек.
- Формат: `https://schema.org/BreadcrumbList`
- Источник данных: иерархия из `location_geo_path` (для САН) или категорий (для RSS-сайтов и grekpanteon).

**JSON-LD FAQPage:**

- На главных страницах и справочных разделах обязательна разметка FAQPage.
- Минимум 5 вопросов/ответов, релевантных тематике сайта.
- Формат: `https://schema.org/FAQPage`

**Детальная разметка ImageObject:**

- Для каждого изображения на сайте обязательна разметка ImageObject.
- Обязательные поля: `contentUrl`, `author` (с `name`), `license`, `source` (URL источника).
- Формат: `https://schema.org/ImageObject`

**Мета-теги для ИИ-краулеров:**

- На всех страницах устанавливается: `<meta name="robots" content="max-image-preview:large">`
- Для страниц с видео добавляется: `<meta property="og:video" content="...">`

**Файл ai-hints.txt:**

- На корневых доменах всех 14 сайтов размещается файл `ai-hints.txt`
- Содержание: явное разрешение на цитирование материалов ИИ-поисковиками при условии указания обратной ссылки
- Формат: plain text с четкими инструкциями для GPTBot, PerplexityBot, ClaudeBot, Google-Extended

## РАЗДЕЛ Z. СТРАТЕГИЯ 301-РЕДИРЕКТОВ

### Z.1 Архитектура редиректов

**Механизм**: Встроенные редиректы на уровне фреймворка Hugo

**Формат**: Файл `_redirects` в корне каждого сайта (формат Netlify)

**Пример**:

/2024/03/vazhnoe-sobyitie.html  /posts/2024/03/vazhnoe-sobyitie/  301

**Альтернативный формат** (через config.toml):

[[redirects]]
  from = "/2024/03/vazhnoe-sobyitie.html"
  to = "/posts/2024/03/vazhnoe-sobyitie/"
  status = 301
  force = true

### Z.2 Генерация Redirect Map

**Обязательный скрипт**: `scripts/generate_redirect_map.py`

**Входные данные**:
- `backup/feed.xml` (сырой дамп Blogger)
- Новая URL-структура из конфига миграции

**Выходные данные**:
- `redirect_map.json` — маппинг старых URL на новые
- `redirects.csv` — для импорта в Cloudflare/Nginx
- `_redirects` — для Hugo/Netlify

**Алгоритм работы**:
1. Парсинг `feed.xml` → извлечение старых URL, заголовков, дат, меток
2. Нормализация заголовков → генерация slug по новым правилам
3. Сопоставление старых URL с новыми на основе:
   - Совпадения slug (если структура похожа)
   - Совпадения заголовка (fuzzy matching)
   - Даты публикации (для временных меток)
4. Генерация JSON/CSV с маппингом
5. Валидация: проверка, что все старые URL имеют соответствие

**Пример выходных данных** (redirect_map.json):

{
  "https://web-moisites.blogspot.com/2023/05/article.html": "/articles/article/",
  "https://web-novosti.blogspot.com/2024/03/news.html": "/posts/2024/03/news/",
  "https://web-joga.blogspot.com/2022/11/asana.html": "/topics/asanas/asana/"
}

### Z.3 Валидация Redirect Map

**Обязательный скрипт**: `scripts/validate_redirect_map.py`

**Проверки**:
- ✅ Все ли старые URL имеют соответствие
- ✅ Нет ли дубликатов новых URL
- ✅ Все ли новые URL валидны (соответствуют структуре)
- ✅ Нет ли циклических редиректов
- ✅ Нет ли цепочек редиректов (A → B → C)

**Пример запуска**:

cd /workspaces/manifests
python scripts/validate_redirect_map.py \
  --input redirect_map.json \
  --base-url https://blagorussia.ru \
  --output validation_report.json

**Выходные данные**:
- `validation_report.json` — детальный отчет с ошибками и предупреждениями
- Консольный вывод с цветной индикацией (✅/❌)

**Критерии успеха**:
- 0 ошибок (блокирующих)
- ≤ 5 предупреждений (неблокирующих)

### Z.4 План отката (Rollback Plan)

Если что-то пойдет не так в день Big Bang:

**Сценарий 1: Массовый сбой всех сайтов**

Скрипт отката: scripts/rollback.sh

Шаги отката:
1. Вернуть noindex на все сайты
2. Отключить редиректы (переименовать _redirects в _redirects.disabled)
3. Откатить деплой через git revert HEAD

**Сценарий 2: Проблемы с отдельными редиректами**

Добавить недостающие редиректы вручную в файл _redirects нужного сайта в формате:
/old/path.html  /new/path/  301

Затем перезапустить деплой:
git add _redirects
git commit -m "fix: добавить недостающий редирект"
git push

**Сценарий 3: Потеря SEO-веса**

Проверить в Яндекс.Вебмастере и Google Search Console:
- Количество проиндексированных страниц
- Количество 404 ошибок
- CTR в поисковой выдаче

Если есть резкое падение:
1. Проверить корректность всех редиректов
2. Отправить sitemap.xml заново
3. Использовать инструмент "Переобход страниц" в Яндекс.Вебмастере
