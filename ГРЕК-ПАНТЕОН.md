- **Этап 3 (Масштабирование):** Оптимизация производительности, переход на PostgreSQL при превышении лимитов Yandex Object Storage, расширение геоинформационного слоя.

## 1. ДАННЫЕ И СХЕМА БАЗЫ ДАННЫХ

### 1.1. Источники данных

- **Первичный источник:** Google Таблица (синхронизация через скрипт `grekpanteon_pipeline.py`).
- **Обогащение:** Wikidata API (извлечение изображений `wdt:P18`, мест жительства `wdt:P551`).
- **Структура данных:** Parquet-файлы в Yandex Object Storage (S3-совместимое хранилище) + обработка через DuckDB (in-memory OLAP).
- **Обоснование:** Отказ от локальных SQLite-файлов в пользу облачного Serverless-подхода. Это обеспечивает бесплатный, версионируемый и производительный слой данных без необходимости администрирования SQL-сервера. На Этапе 3 (при превышении лимитов) возможен переход на PostgreSQL.

### 1.3. Таблица причинно-следственных связей (ИИ-генерация)

```sql
CREATE TABLE character_causal_links (
 id INTEGER PRIMARY KEY,
 cause_character_id INTEGER REFERENCES characters(id),
 effect_character_id INTEGER REFERENCES characters(id),
 event_description TEXT NOT NULL,
 causal_type TEXT NOT NULL, -- 'direct', 'indirect', 'triggered', 'prevented'
 event_date INTEGER,
 source_id INTEGER REFERENCES sources(id),
 confidence_score REAL DEFAULT 1.0,
 created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 1.4. Критерии публикации (жёсткие)

| Тип персонажа | Минимальная длина текста | Минимальное количество изображений |
|---------------|--------------------------|-------------------------------------|
| Известные (исторические / мифологические) | ≥ 800 знаков | ≥ 1 |
| Малоизвестные (`is_minor_character = TRUE`) | ≥ 500 знаков | ≥ 1 |

**Определение `is_minor_character`** (автоматическое + ручное):

- **Автоматически:** если у персонажа ≤ 2 источников И он не член династического дома (или относится к категориям `minor-deities`, `monsters`).
- Администратор может переопределить флаг вручную (поле `minor_character_override_by`).

### 1.5. Стратегия двухэтапной миграции данных

#### 1.5.1. Этап 1: Статический дамп (Hugo)

На первом этапе миграции сайт разворачивается как статический дамп:

1. Данные из текущей БД (SQLite/Google Таблицы) экспортируются в статические HTML-файлы.
2. Все изображения проходят Image Sanitization Pipeline (согласно САМ п.2.5).
3. Генерируются sitemap-файлы по принципу батчинга по ID (5000 URL/файл).
4. Сохраняются все существующие URL (slug) для SEO-преемственности.
5. Вся структура публикации (типы персонажей, категории, источники) сохраняется.

**Ограничения Этапа 1:**

- ❌ Отсутствует ИИ-конвейер генерации описаний
- ❌ Отсутствуют причинно-следственные связи
- ❌ Отсутствует геоинформационный слой
- ❌ Отсутствует интерактивность (комментарии, поиск, фильтрация)

#### 1.5.2. Этап 2: Полноценная версия на Astro

На втором этапе статическая версия постепенно замещается полноценной архитектурой на Astro:

1. **ETL-конвейер:** Скрипт `grekpanteon_pipeline.py` выгружает данные из Google Sheets в Parquet-файлы (Yandex Object Storage).
2. **Сборка:** Astro (через контент-коллекции) читает JSON/Markdown артефакты.
3. **Функционал:** Активируются интерактивные острова (Islands) для графов и карт.

## 4. ИИ-КОНВЕЙЕР И ОБРАБОТКА ДАННЫХ

### 4.1. Генерация описаний (RAG-пайплайн)

- **Системный промпт:** на основе предоставленных источников древнегреческой литературы написать структурированное описание персонажа (происхождение, основные мифы, роль в пантеоне/династии/доме, упоминания в литературе). Научно-популярный стиль. Объём: 500–800 слов.
- **ИИ-модель:** Gemini API (с возможностью переключения через `IAiProviderGateway` согласно принципу AI-Provider Agnostic из САМ).

### 4.2. Генерация причинно-следственных связей

- **Скрипт:** `scripts/generate_causal_links.py` (Gemini API).
- **Типы связей:** `direct` (прямое действие), `indirect` (косвенное), `triggered` (спровоцировало), `prevented` (предотвратило).
- **Визуализация:** компонент `hugo/layouts/partials/causal-graph.html` (интерактивный граф).

### 4.3. Извлечение источников изображений (обязательная атрибуция)

- **Скрипт:** `scripts/image_source_extractor.py`.
- **Уровни получения:**
 - **4.3.a.** Google Таблица (основной): связь `characters.source_id` → `sources.external_url`.
 - **4.3.b.** Wikidata API (обогащение): для персонажей с `wikidata_id` – получение `wdt:P18` (изображение), `wdt:P551` (место жительства).
 - **4.3.c.** Ручная атрибуция: для фото Боброва А.В. – жёстко фиксируется в Тематическом паспорте.

## 5. ПУБЛИКАЦИЯ И SITEMAP

### 5.1. Суточный лимит и подэтапы

- **Лимит:** 200 новых страниц в сутки (обеспечивает контроль качества и индексацию).
- **Подэтапы:** разбивка по батчингу ID (5000 URL на файл sitemap).

### 5.2. Структура sitemap

Sitemap формируется по принципу **батчинга по ID** (5000 URL/файл), **НЕ** по коленам (поколениям) и **НЕ** по алфавиту.

**Обоснование:**

- Колено (generation) может меняться при обновлении генеалогических данных → 404 ошибки и пессимизация Google.
- Алфавитное распределение неравномерно (буква «А» – 2000 персонажей, буква «Я» – 50).
- Батчинг по ID обеспечивает стабильность URL, равномерное распределение и быструю генерацию.

**Структура `sitemap_index.xml`:**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<sitemapindex xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
 <!-- По типам сущностей (стабильно) -->
 <sitemap>
 <loc>https://grekpanteon.obrazslov.ru/sitemap-mythological-characters.xml</loc>
 <lastmod>2026-07-09</lastmod>
 </sitemap>
 <sitemap>
 <loc>https://grekpanteon.obrazslov.ru/sitemap-historical-characters-001.xml</loc>
 <lastmod>2026-07-09</lastmod>
 </sitemap>
 <sitemap>
 <loc>https://grekpanteon.obrazslov.ru/sitemap-historical-characters-002.xml</loc>
 <lastmod>2026-07-09</lastmod>
 </sitemap>
 <!-- ... (по числу батчей) -->
 <sitemap>
 <loc>https://grekpanteon.obrazslov.ru/sitemap-dynasty-houses.xml</loc>
 <lastmod>2026-07-09</lastmod>
 </sitemap>
 <sitemap>
 <loc>https://grekpanteon.obrazslov.ru/sitemap-locations.xml</loc>
 <lastmod>2026-07-09</lastmod>
 </sitemap>
 <sitemap>
 <loc>https://grekpanteon.obrazslov.ru/sitemap-sources.xml</loc>
 <lastmod>2026-07-09</lastmod>
 </sitemap>
</sitemapindex>

- **Скрипт генерации:** `scripts/generate_sitemaps.py` (батчинг по 5000 URL с OFFSET/LIMIT).
- Автоматический ping поисковиков после каждого подэтапа выполняется скриптом `scripts/ping_search_engines.py` (описан в Манифесте СУМКа).

## 6. SEO И СЕМАНТИЧЕСКИЕ URL

### 6.1. Новые ЧПУ (человеко-читаемые URL)

| Маршрут | Назначение |
|---------|------------|
| `/character/{slug}/` | Персонаж (мифологический или исторический) |
| `/source/{slug}/` | Источник (античный или современный труд) |
| `/dynasty/{slug}/` | Династический дом |
| `/location/{slug}/` | Географическая локация |
| `/epics/{slug}/{song}/` | Эпосы с навигацией Book/Chapter |

### 6.2. 301-редиректы

- Карта соответствия старых URL (Blogger / старые версии) → новые ЧПУ хранится в `migration_seo_map.json`.
- Next.js / Hugo Middleware выполняет автоматический 301-редирект.

### 6.3. JSON-LD разметка (три типа страниц)

- **Мифологический персонаж:** `Person` + `hasOccupation` (бог/герой/чудовище) + `mentions` (источники).
- **Исторический персонаж:** `Person` + `hasOccupation` (царь/полководец/философ) + `memberOf` (династический дом).
- **Династический дом:** `Organization` + `founder` (мифологический герой-родоначальник) + `foundingDate`.

### 6.4. Расширенная семантическая разметка для ИИ-поисковиков (GEO)

#### 6.4.1. JSON-LD BreadcrumbList

На всех страницах персонажей и категорий обязательна разметка хлебных крошек:

```json
{
 "@context": "https://schema.org",
 "@type": "BreadcrumbList",
 "itemListElement": [
 { "@type": "ListItem", "position": 1, "name": "Главная", "item": "https://grekpanteon.obrazslov.ru/" },
 { "@type": "ListItem", "position": 2, "name": "Мифологические персонажи", "item": "https://grekpanteon.obrazslov.ru/category/mythological/" },
 { "@type": "ListItem", "position": 3, "name": "Зевс", "item": "https://grekpanteon.obrazslov.ru/character/zeus/" }
 ]
}

#### 6.4.2. Детальная разметка ImageObject

Для каждого изображения на сайте обязательна разметка `ImageObject` с полной атрибуцией:

```json
{
 "@type": "ImageObject",
 "contentUrl": "https://grekpanteon.obrazslov.ru/images/zeus.webp",
 "author": { "@type": "Person", "name": "Античный скульптор (неизвестен)" },
 "license": "https://creativecommons.org/publicdomain/mark/1.0/",
 "source": "https://www.wikidata.org/wiki/Q3409"
}
```

#### 6.4.3. Мета-теги для ИИ-краулеров

На всех страницах устанавливается мета-тег:

```html
<meta name="robots" content="max-image-preview:large">
```

#### 6.4.4. Файл `ai-hints.txt`

На корневом домене `grekpanteon.obrazslov.ru` размещается файл `ai-hints.txt` с явным разрешением на цитирование материалов ИИ-поисковиками при условии указания обратной ссылки.

#### 6.4.5. Стандарт для сайта-витрины `gallery.obrazslov.ru`

Для сайта-витрины НКО `gallery.obrazslov.ru` применяются следующие дополнительные требования:

1. **Главная страница:** разметка `ImageGallery` с полными метаданными (`publisher`, `author`, `license`, `hasPart`).
2. **Страница FAQ:** разметка `FAQPage` с ответами на часто задаваемые вопросы (минимум 3 вопроса).
3. **Хлебные крошки:** `BreadcrumbList` для всех страниц, кроме главной.
4. **Блок раскрытия интересов:** обязательный визуальный блок с предупреждением о некоммерческом характере архива.
5. **Атрибуция изображений:** для каждого изображения, экспортируемого из Пантеона, в JSON-LD указывается:
 - `author`: автор изображения (античный скульптор, художник или "Неизвестен")
 - `license`: лицензия (CC BY 4.0 или Public Domain)
 - `source`: источник (URL из `sources.external_url` или Wikidata)
 - `description`: описание изображения с указанием персонажа и источника

## 7. ОБЯЗАТЕЛЬНАЯ АТРИБУЦИЯ ИЗОБРАЖЕНИЙ

### 7.1. Регламент

Для всех изображений на `grekpanteon.obrazslov.ru` **ОБЯЗАТЕЛЬНО** указание источника в:

### 7.2. Обоснование

1. **E-E-A-T:** Google и ИИ-поисковики приоритизируют контент с прозрачной атрибуцией источников.
2. **Авторское право:** Защита от претензий по DMCA.
3. **GEO:** ИИ-поисковики цитируют только источники с явным `author`, `license`, `url`.
4. **Соответствие САМ:** принцип 3.12 (юридический комплаенс).

### 7.3. Техническая реализация

1. Hugo-шаблон: `hugo/layouts/partials/image-with-source.html`.
2. Скрипт извлечения: `scripts/image_source_extractor.py` (описан в п.4.3).

### 7.4. Обработка изображений через Image Sanitization Pipeline

Обработка изображений Пантеона выполняется согласно принципу 2.5 САМ (Image Sanitization Pipeline). Подробное руководство: `/docs/IMAGE_SANITIZATION_GUIDE.md`.

**Краткое описание этапов:**

1. EXIF-очистка (`exiftool -all=`)
2. Конвертация в WebP/AVIF (`sharp`/`cwebp`)
3. Ресайз до 4 размеров (400, 800, 1200, 1600px) с обязательным ≤1600px для активации безлимитного хранения на Blogger
4. Детекция дубликатов (pHash + Hamming distance)
5. Водяной знак (опционально, по флагу)

**Обязательные HTML-атрибуты для всех изображений Пантеона:**

| Атрибут | Назначение |
|---------|------------|
| `alt` | Текстовое описание с указанием источника для поисковиков и скринридеров |
| `title` | Всплывающая подсказка при наведении |
| `loading="lazy"` | Отложенная загрузка (кроме Hero) |
| `fetchpriority="high"` | Приоритетная загрузка Hero (LCP) |
| `decoding="async"` | Асинхронное декодирование |
| `width` / `height` | Предотвращение CLS |
| `srcset` + `sizes` | Адаптивные изображения |
| `itemprop="image"` | Микроразметка Schema.org |
| `data-caption` | Подпись к изображению с указанием источника |

### 7.5. Хранение изображений

Хранение всех изображений Пантеона выполняется согласно САМ (п. 2.4 «Эволюционная модель хранения медиа»).

**Ключевые положения:**

- Все изображения загружаются в Blogger как основное хранилище (0 ₽, безлимит при ресайзе ≤1600px).
- Cloudflare R2 используется только для PDF-документов (если есть) и медиа-паспортов.
- Изображения Пантеона дублируются на сайте-витрине НКО `gallery.obrazslov.ru` с использованием:
 - Тематических страниц по 50 изображений.
 - Навигации через labels (теги).
 - Полной атрибуции авторства и лицензии в JSON-LD (`ImageObject`).
 - Блока «Раскрытие интересов» на каждой странице.
- Сайт-витрина НКО `gallery.obrazslov.ru` позиционируется как **ФОТОАРХИВ НКО** — централизованное хранилище изображений всех проектов экосистемы.
- Защита от vendor lock-in обеспечивается скриптом `migrate_blogger_to_r2.py` и еженедельным бэкапом метаданных в `shared-assets/blogger_image_metadata.json` (Git).
