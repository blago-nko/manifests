1. Назначение
Этот документ является единым источником правды для архитектурных решений экосистемы НП «Общественное благополучие» (blago-nko). Все технические решения должны соответствовать данному манифесту. Любые отклонения требуют обоснования и утверждения через Pull Request.
2. Технологический стек
2.1. Для контентных сайтов (статическая генерация)
Основной инструмент: Hugo (версия ≥ 0.164.0)
Лицензия: Apache 2.0
Применение:
ГРЕК-ПАНТЕОН (пантеон греческой мифологии)
web-news (новостной портал)
web-ideology (Новая идеология)
web-history (Наша история)
web-yoga (Новая йога)
web-classifieds (Объявления)
web-interesting-places (Интересные места)
obrazslov.ru (культурно-образовательный портал)
blagorussia.ru (общественный портал)
Обоснование выбора Hugo:
Скорость сборки: тысячи страниц генерируются за миллисекунды (на Go)
Простота установки: один бинарный файл, без зависимостей Node.js
Стабильность: сайт документации gohugo.io работает без сбоев (в отличие от astro.build)
Встроенная таксономия: категории, теги, серии — идеально для энциклопедий
Мультиязычность: i18n из коробки (важно для мифологии и истории)
Cross-references: автоматические связи между страницами (боги → мифы → герои)
Русскоязычная документация: полная локализация на gohugo.io
Активное сообщество: 89,000+ звёзд на GitHub
Альтернативы (допустимы при обосновании):
Astro — для проектов с высокой интерактивностью (Islands Architecture)
Eleventy (11ty) — для простых проектов на чистом JavaScript
2.2. Для динамических приложений
Основной инструмент: Next.js (версия ≥ 15.x, App Router)
Лицензия: MIT
Применение:
САН (Система Администрирования и Наблюдения) — админ-панель
Личные кабинеты пользователей
Интерактивные сервисы с авторизацией
Проекты с real-time обновлениями
Обоснование выбора Next.js:
React компоненты: для сложного UI (таблицы, графики, формы)
API Routes / Server Actions: встроенный бэкенд
Server-Side Rendering (SSR): быстрая загрузка динамического контента
Аутентификация: NextAuth.js / Auth.js
TypeScript: строгая типизация для сложных данных
Документация на русском: nextjs.org полностью локализован
Экосистема Vercel: удобный деплой и мониторинг
Альтернативы (допустимы при обосновании):
React Admin — готовый фреймворк для админок
Refine — headless админ-фреймворк
Remix — если предпочитаете веб-стандарты
2.3. Общие ресурсы
Пакет: packages/shared
Содержимое:
UI компоненты (кнопки, карточки, навигация)
Утилиты (форматирование дат, валидация)
Стили (CSS переменные, дизайн-система)
Скрипты (аналитика, SEO, метрики)
Шаблоны писем и уведомлений
Технологии:
TypeScript (общий для всех пакетов)
Tailwind CSS (единая дизайн-система)
Lucide Icons (единый набор иконок)

2.5. Хостинг и деплой
Платформа:
Статические сайты (Hugo): Cloudflare Pages (бесплатно, глобальный CDN)
Динамические приложения (Next.js): Vercel или Cloudflare Pages (с SSR)
Админ-панель (САН): Vercel (с авторизацией)
CI/CD: GitHub Actions
Домены: Настройка через DNS провайдера (blagorussia.ru, obrazslov.ru)

3.2. Ветки
Стратегия: GitHub Flow (упрощённый)
main — продакшн ветка (защищена, только через PR)
feature/{description} — новые функции
fix/{description} — исправления багов
hotfix/{description} — срочные исправления продакшна
docs/{description} — изменения в документации
Примеры:
feature/add-gods-taxonomy
fix/typo-in-zeus-article
docs/update-САМ-manifest
3.3. Коммиты
Формат: Conventional Commits
<type>(<scope>): <description>

[optional body]

[optional footer]
ипы:
feat: — новая функция
fix: — исправление бага
docs: — изменения в документации
style: — форматирование, без изменения кода
refactor: — рефакторинг кода
test: — добавление тестов
chore: — изменения в сборке, зависимостях
content: — добавление/изменение контента (для Hugo сайтов)
Примеры:
feat(web-news): add article filtering
fix(grek-panteon): correct Zeus genealogy
docs(САМ): update technology stack to Hugo
content(grek-panteon): add Athena article

6. Процесс внесения изменений в архитектуру
Создать Issue в GitHub с описанием архитектурного изменения
Обсудить с командой (минимум 2 approval от maintainers)
Внести изменения в САМ.md через Pull Request
Обновить связанные документы (СУМКа, САН, ЛИЦ)
Пройти CI проверки (линтинг, сборка)
Слить PR в main
Уведомить команду об изменениях (через GitHub Discussions или чат)
Обновить CHANGELOG.md в корне монорепозитория
