## 1. ВВЕДЕНИЕ

### 1.1. Миссия экосистемы

Экосистема создана Некоммерческим партнёрством «Общественное благополучие Воронежа» для реализации общественно значимых проектов в сферах историко-биографического просвещения, образования, поддержки гражданских инициатив и развития агентского сообщества в недвижимости.

### 1.2. Состав экосистемы (14 доменов)

a. **11 RSS-сайтов** основной сети (Hugo + GitHub Pages): `blagorussia.ru`, `obrazslov.ru`, `partnerstvo`, `novosti`, `ot-gorozan`, `obavlenia`, `interesnye-mesta`, `moisites`, `joga`, `ideologia`, `nasa-istoria`.

b. **`grekpanteon.obrazslov.ru`** (Astro + GitHub Pages) — база знаний по античной мифологии (16 505+ страниц).

c. **`can.blagorussia.ru`** (Next.js + Vercel) — платформа САН. Изолированный контур (`can-secure-dev`) для работы с ПДн (152-ФЗ).

d. **`gallery.obrazslov.ru`** (Blogger) — витрина НКО, тематический каталог изображений.

### 1.3. Технологический стек (Обновление v2.0)

- **Контентные сайты (11 RSS):** Hugo (статическая генерация, высокая скорость, таксономия).
- **Пантеон:** Astro (статическая генерация, архитектура островов, полная совместимость с shared-assets).
- **Динамические приложения (САН):** Next.js App Router (SSR, Edge Middleware, API Routes).
- **Хранение медиа:** Blogger (основное, безлимит при ресайзе ≤1600px) + Cloudflare R2 (PDF, медиа-паспорта).
- **Базы данных:** PostgreSQL/Supabase (САН) + SQLite (Пантеон).

### 1.4. 77 архитектурных принципов

Полный перечень принципов сгруппирован по четырём направлениям и приведён в **Приложении А**. Ключевые сквозные принципы:

- **2.4** Эволюционная модель хранения медиа (Blogger + R2)
- **2.5** Image Sanitization Pipeline (5 этапов)
- **3.1** Единый источник правды и кросс-манифестная синхронизация
- **4.11** Mobile-First (проектирование от xs:320px)

### 2.2. Эволюционная модель хранения медиа (Единый источник правды)

- Все изображения экосистемы загружаются в **Blogger** как основной слой.
- **Условие безлимита:** Image Sanitization Pipeline обязан ресайзить все изображения до **≤1600px** (гарантирует ≤2048px — лимит Google).
- **Cloudflare R2:** Только для PDF-документов и `media_passport.json.gz`.
- **Защита от vendor lock-in:** Скрипт `migrate_blogger_to_r2.py` + еженедельный бэкап метаданных в Git.

### 2.3. Image Sanitization Pipeline (Единый конвейер)

Каждое изображение проходит 5 этапов:

1. EXIF-очистка (`exiftool -all=`)
2. Конвертация в WebP/AVIF (`sharp`/`cwebp`)
3. Ресайз до 4 размеров (400, 800, 1200, 1600px)
4. Детекция дубликатов (pHash + Hamming distance)
5. Водяной знак (опционально, по флагу)

### 2.4. Единый стандарт фронтенда (Shared Assets)

- Все 14 сайтов используют репозиторий `blago-nko/shared-assets`.
- **Структура:** `templates/`, `css/` (11 тем + `mobile.css`), `js/`, `jsonld/`, `seo/`, `components/`, `favicons/`, `legal/`.
- **Ссылки:** Внутренние домены экосистемы открываются в том же окне (`target="_self"`), внешние — в новом (`target="_blank"`).
- **Favicon:** Единый для всех 14 сайтов.

#### 2.4.1. Совместимость с SSG-фреймворками

Для контентных проектов с большим количеством страниц (>10 000), к которым относится `grekpanteon.obrazslov.ru`, утверждён генератор статических сайтов **Astro**.

- **Обоснование:** Astro использует стандартные веб-технологии (HTML/CSS/JS) и позволяет напрямую импортировать компоненты из `blago-nko/shared-assets` (шаблоны, стили, JSON-LD генераторы), что обеспечивает 100% визуальную консистентность и соблюдение принципа DRY (п. 2.8).
- **Запрет на изолированные шаблонизаторы:** Использование фреймворков с проприетарными шаблонизаторами (Hugo/Go-templates, Jekyll/Ruby) для крупных контентных проектов не допускается, так как они не поддерживают прямую интеграцию с `shared-assets` и ведут к дублированию кода.
- **Исключение:** 11 RSS-сайтов продолжают использовать Hugo, так как их структура позволяет генерировать статические страницы с минимальной кастомизацией шаблонов. При масштабировании RSS-сайтов до >10 000 страниц требуется миграция на Astro.

## 3. УПРАВЛЕНИЕ И РАЗВИТИЕ

### 3.1. Архитектурный комитет и процесс изменений

- Высший орган — **Архитектурный комитет Партнерства** (председатель: А.В. Бобров, право вето).
- Изменения вносятся только через **Протокол архитектурных изменений** с префиксами (`SAM-`, `MIG-`, `SAN-`, `SUMKA-`, `GP-`).
- Обязательна **кросс-манифестная синхронизация:** если меняется общий принцип (например, хранение), он обновляется во всех 5 манифестах.

### 3.2. CI/CD и тестирование

- **RSS-сайты и Пантеон:** GitHub Pages (push в `main` или `gh-pages`).
- **САН:** Vercel (PaaS) под аккаунтом `can-secure-dev`.
- **Gallery:** Blogger с кастомным доменом.
- **Автоматизация:** GitHub Actions для бэкапа метаданных Blogger, авто-обновления `STATUS.md`, линтинга и Playwright E2E-тестов.

---

### 3.3. Техническая инфраструктура кросс-организационного единообразия

Экосистема физически распределена между несколькими GitHub-организациями:

- **@blago-nko** — основная сеть (общественные порталы, культурно-образовательные проекты);
- **@can-secure-dev** — платформа САН (Сообщество Агентов Недвижимости).

Единообразие между организациями обеспечивается следующими техническими механизмами.

#### 3.3.1. Единый реестр артефактов (GitHub Packages)

- Репозиторий `blago-nko/shared-assets` публикует общие компоненты, стили, утилиты и конфигурации в приватный npm-реестр GitHub Packages (`npm.pkg.github.com`).
- Все проекты экосистемы (включая @can-secure-dev) подключают артефакты как зависимости через `package.json`.
- Версионирование артефактов — семантическое (SemVer).
- Breaking changes допускаются только через протокол `MIG-` с предварительным уведомлением всех потребителей.
- Доступ к реестру предоставляется через Fine-grained PAT или GitHub App с минимальными правами (`read:packages`).

#### 3.3.2. Reusable Workflows (единый CI/CD-фреймворк)

Все репозитории экосистемы обязаны использовать общие GitHub Actions Workflows, размещённые в `blago-nko/.github/workflows/`:

| Workflow | Назначение | Триггер |
| --- | --- | --- |
| `architecture-check.yml` | Валидация кода на соответствие манифестам | PR opened/sync |
| `protocol-check.yml` | Проверка префиксов PR (`SAM-`, `SAN-`, `MIG-`...) | PR opened |
| `sync-manifests.yml` | Рассылка обновлений манифестов в зависимые репо | push в manifests |
| `publish-assets.yml` | Публикация shared-assets в GitHub Packages | push в shared-assets |
| `ai-rules-sync.yml` | Обновление `.cursorrules` / `copilot-instructions.md` | push в САН §12 |

Каждый Pull Request в любой репозиторий экосистемы обязан проходить этап `architecture-check`, который:

1. Скачивает актуальную версию `manifests` из @blago-nko.
2. Запускает линтер, проверяющий:
   - наличие обязательных JSON-LD разметок;
   - соответствие лимитам БД и требованиям 152-ФЗ;
   - наличие тестов на изменённые модули;
   - соблюдение префиксов протокола в заголовке PR.
3. Устанавливает статус `architecture-check` как Required Status Check для мержа.

#### 3.3.3. GitHub App: Blago Ecosystem Bot

Для кросс-организационного взаимодействия используется единый GitHub App (`Blago Ecosystem Bot`), установленный в каждую организацию экосистемы.

**Права приложения:**

- `contents: read` — чтение кода и манифестов;
- `checks: write` — установка статусов проверок;
- `pull_requests: write` — управление labels, блокировка мержа;
- `issues: read` — чтение связанных Issues.

**Логика блокировки:**

- Если `architecture-check` = failure → устанавливается label `🚫 протокол нарушен`, мерж блокируется.
- Если в заголовке PR отсутствует валидный префикс → устанавливается label `⚠️ нет префикса`, мерж блокируется.
- Если PR не связан с утверждённым Issue → мерж блокируется.

#### 3.3.4. Политика секретов и доступа

- Секреты (токены, ключи) хранятся в GitHub Secrets каждой организации.
- Ротация токенов — каждые 90 дней.
- Доступ к secrets — только у Архитектурного комитета.
- Запрещено:
  - хранить токены в исходном коде;
  - передавать секреты в открытом виде между репозиториями;
  - использовать один токен для нескольких организаций без разделения прав.

| Секрет | Организация | Назначение |
| --- | --- | --- |
| `BLAGO_NPM_TOKEN` | @can-secure-dev | Чтение GitHub Packages @blago-nko |
| `MANIFESTS_PAT` | @can-secure-dev | Клонирование manifests в CI |
| `ARCHIVE_KEY` | @blago-nko | Шифрование бэкапов |

#### 3.3.5. Синхронизация инструкций для ИИ-агентов

- В корне каждого репозитория экосистемы обязан присутствовать файл `.github/copilot-instructions.md` (или `.cursorrules`).
- Содержимое файла автоматически генерируется из раздела 12 манифеста САН.
- При каждом обновлении САН § 12 GitHub Actionai-rules-sync.yml рассылает обновлённые инструкции во все репозитории экосистемы.
- ИИ-агентам ЗАПРЕЩЕНО генерировать код, нарушающий текущие пункты манифеста, без вывода блока «ПРЕДЛОЖЕНИЕ ПО ИЗМЕНЕНИЮ МАНИФЕСТА» (см. САН § 12).

#### 3.3.6. Мониторинг и отчётность

- Еженедельный GitHub Action генерирует отчёт `STATUS.md` в `manifests/reports/`:
  - количество PR, заблокированных из-за нарушения протокола;
  - версии shared-assets в каждом проекте;
  - дата последней синхронизации манифестов;
  - статус feature flags по проектам.
- Отчёт доступен Архитектурному комитету для принятия решений.

## 4. ВЛОЖЕННЫЕ МАНИФЕСТЫ

Экосистема управляется специализированными манифестами, которые являются неотъемлемыми частями САМ:

- **Манифест миграции** — план переноса 14 доменов.
- **Манифест САН** — архитектура платформы недвижимости (Next.js, RESO, 152-ФЗ).
- **Манифест Грек-Пантеон** — база знаний (Astro, SQLite, ИИ-конвейер).
- **Манифест СУМКа** — дистрибуция контента в соцсети и фиды.

В случае противоречий приоритет имеет **САМ**.

### Г1. Общие положения

Настоящая Политика конфиденциальности (далее — Политика) определяет порядок обработки и защиты персональных данных пользователей всех 14 сайтов экосистемы Некоммерческого партнёрства «Общественное благополучие Воронежа».

Политика разработана в соответствии с Федеральным законом от 27.07.2006 № 152-ФЗ «О персональных данных».

Политика размещается на всех сайтах экосистемы по адресу: `/p/privacy-policy.html`.

### Г2. Категории обрабатываемых данных

**Для всех пользователей (включая незарегистрированных):**

- IP-адрес,
- тип браузера и операционной системы,
- время доступа,
- посещённые страницы,
- реферер (откуда пришёл пользователь).

**Для зарегистрированных пользователей (заявители):**

- Имя, фамилия,
- номер телефона (шифруется AES-256-GCM),
- адрес электронной почты (шифруется AES-256-GCM),
- предпочтения по недвижимости (тип, район, цена).
