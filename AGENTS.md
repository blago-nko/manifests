## Инструкции для ИИ-агентов

> **ВАЖНО:** Этот файл обязателен к прочтению для всех ИИ-агентов
> (Claude, GPT, Gemini и др.), работающих с этим репозиторием.

## 🌩️ Облачная разработка (Cloud-Only Development)

Вся разработка в экосистеме blago-nko ведётся **исключительно в облаке**.

### Обязательные правила

**ЗАПРЕЩЕНО**

- Локальная разработка на рабочей машине.
- Клонирование репозиториев на локальный диск (`git clone`).
- Использование локальных IDE (VS Code desktop, IntelliJ IDEA, WebStorm и т.д.).
- Локальные коммиты и push (`git commit`, `git push`) из терминала локальной машины.
- Хранение Personal Access Tokens в локальных конфигурациях, `.env`-файлах или keyring ОС.
- Прямой коммит в ветку `main` любого репозитория экосистемы.

**ОБЯЗАТЕЛЬНО:**

- Google Colab или Jupyter notebooks для всей разработки
- GitHub API для всех изменений файлов
- Personal Access Tokens для аутентификации
- Обработка всех данных в памяти (RAM), без сохранения на диск

## 🧩 Формат выдачи кода ИИ-агентом

ИИ-агент ОБЯЗАН выдавать код **по частям (ячейками)** для Google Colab.
Один монолитный скрипт вместо набора ячеек — нарушение стандарта.

### Стандартная структура ответа с кодом

- **Ячейка 1 — Настройки:** импорты, токен, константы, проверка токена
- **Ячейка 2 — Данные:** тексты, шаблоны, содержимое файлов
- **Ячейка 3 — Функции:** вспомогательные функции работы с GitHub API
- **Ячейка 4 — Выполнение:** основной цикл / главная логика
- **Ячейка 5 — Проверка:** контроль результата (GET-запросы, отчёт)

### Правила оформления ячеек

1. Каждая ячейка нумеруется и имеет заголовок («Ячейка N — ...»).
2. Порядок запуска указывается явно («выполняйте по порядку»).
3. В конце каждой ячейки — `print("✅ Ячейка N готова...")` для контроля.
4. Токен указывается ТОЛЬКО в ячейке 1 (настройки), нигде больше.
5. Ячейка либо самодостаточна, либо явно ссылается на предыдущие
   («использует переменные из ячейки 1»).
6. Длинные тексты и шаблоны выносятся в отдельную ячейку-данные,
   а не встраиваются в логику.
7. Если задача простая — допустимо 2–3 ячейки вместо пяти,
   но разделение «настройки / выполнение / проверка» сохраняется.

### Причины

- Пользователь работает в Colab без локального окружения
- Частичный перезапуск при ошибках без потери состояния
- Прозрачность: видно, какой шаг что делает
- Безопасность: токен изолирован в одной ячейке

## 🔐 Рабочий процесс (шаблон для Colab)

```python
import requests
import base64

GITHUB_TOKEN = "ваш_токен"  # https://github.com/settings/tokens
OWNER = "blago-nko"

HEADERS = {
    "Authorization": f"token {GITHUB_TOKEN}",
    "Accept": "application/vnd.github.v3+json",
    "Content-Type": "application/json"
}

def read_file(repo, path):
    url = f"https://api.github.com/repos/{OWNER}/{repo}/contents/{path}"
    resp = requests.get(url, headers=HEADERS)
    if resp.status_code == 200:
        return base64.b64decode(resp.json()['content']).decode('utf-8')
    return None

def write_file(repo, path, content, message):
    url = f"https://api.github.com/repos/{OWNER}/{repo}/contents/{path}"
    sha_resp = requests.get(url, headers=HEADERS)
    sha = sha_resp.json().get('sha') if sha_resp.status_code == 200 else None
    data = {
        "message": message,
        "content": base64.b64encode(content.encode('utf-8')).decode('utf-8'),
        "branch": "main"
    }
    if sha:
        data["sha"] = sha
    resp = requests.put(url, headers=HEADERS, json=data)
    return resp.status_code in [200, 201]
```

## 🔑 Безопасность токенов

- Никогда не коммитьте токены в репозиторий
- Создавайте токены с минимальными правами (`repo` + `workflow`)
- Удаляйте токены после завершения работы

## 5. ПОРЯДОК ВНЕСЕНИЯ ИЗМЕНЕНИЙ В МАНИФЕСТЫ (Manifests-Only Web UI Policy)

Репозиторий `blago-nko/manifests` является высшим органом архитектурного права экосистемы. Для обеспечения максимальной прозрачности, аудируемости и защиты от несанкционированных локальных правок вводится строгая политика.

### 🚫 Жесткий запрет на локальную разработку манифестов

ИИ-агентам и разработчикам **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО**:

1. Клонировать репозиторий `blago-nko/manifests` на локальные машины.
2. Создавать локальные ветки (`git checkout -b`) для редактирования текстов манифестов.
3. Делать локальные коммиты и выполнять `git push` в этот репозиторий из IDE (VSCode, Cursor и т.д.) или терминала.

### ✅ Единственный легальный способ: GitHub Web UI

Все изменения в манифесты (САМ, САН, СУМКа, ГРЕК-ПАНТЕОН, МИГРАЦИЯ, ЛИЦ) вносятся **исключительно через встроенный редактор GitHub (Web UI)** по следующему протоколу:

1. **ИИ-агент генерирует точечные инструкции** (какой файл открыть, какую строку найти, на какой текст заменить) или предоставляет **готовый блок Markdown-кода**.
2. **Пользователь (Человек)** открывает нужный файл на GitHub, нажимает `Edit this file` (карандаш), вставляет изменения и создает коммит прямо в браузере.
3. **Создание ветки:** Коммит делается не в `main`, а в новую ветку, создаваемую через Web UI (опция *Create a new branch for this commit and start a pull request*). Имя ветки должно строго соответствовать протоколу: `chore/SAM-XXX-description` или `fix/MIG-XXX-description`.
4. **Pull Request:** Из Web UI создается PR, в тело которого вставляется сгенерированный ИИ-агентом шаблон с описанием изменений и затронутыми разделами.

### 🤖 Поведение ИИ-агента при запросе на изменение манифеста

Если пользователь или другой агент просит изменить манифест, ИИ-агент обязан:

1. **Не пытаться** применять изменения к локальным файлам (так как их не должно быть на диске).
2. Вывести в чат блок «⚠️ ТРЕБУЕТСЯ ПРАВКА МАНИФЕСТА (Web UI Protocol)» в формате:

```text
⚠️ ТРЕБУЕТСЯ ПРАВКА МАНИФЕСТА (Web UI Protocol)
Файл: [Имя файла.md]
Префикс протокола: [SAM-/SAN-/GP-/MIG-/LITS-CHORE-XXX]

ИНСТРУКЦИЯ ДЛЯ ЧЕЛОВЕКА:
1. Перейдите по ссылке: [URL файла на GitHub]
2. Нажмите карандаш (Edit).
3. Найдите блок: [старый текст]
4. Замените на: [новый готовый блок Markdown]
5. Внизу выберите "Create a new branch" и назовите её: chore/префикс-описание.
6. Нажмите "Propose changes".
```

### 5.1 Работа с ветками и Pull Request (Branch Protocol)

Все изменения в манифесты вносятся исключительно через **Pull Request** из отдельной ветки. Прямой коммит в `main` категорически запрещён и будет заблокирован Branch Protection Rules.

#### 🌿 Правило именования веток

Имя ветки должно строго соответствовать шаблону:

```text
<тип>/<ПРОТОКОЛ>-<краткое-описание>
```

**Типы веток:**

- `fix/` — исправление противоречий, ошибок, синхронизация
- `chore/` — технические правки (обновление дат, форматирования)
- `docs/` — изменения документации без архитектурных правок

**Примеры корректных имен:**

- `fix/SAM-FIX-001-version-sync`
- `fix/GP-FIX-002-hugo-first-strategy`
- `fix/SAN-FIX-003-db-budget-recalc`
- `fix/SAN-FIX-004-bytea-152fz`
- `fix/MIG-FIX-005-tracks-separation`
- `fix/LIC-FIX-006-dual-licensing`
- `chore/DOCS-CHORE-007-readme-sync`
- `docs/SUMKA-CHORE-008-markdown-cleanup`

**Запрещено использовать:**

- `patch-1`, `update-readme`, `fix-branch` (без префикса протокола)
- Имена с пробелами или спецсимволами

#### 📝 Правило атомарности

**1 протокол = 1 ветка = 1 PR**

Запрещено объединять несколько протоколов в одном PR. Каждый протокол из ПАИ (Протокола Архитектурных Изменений) должен быть выполнен отдельным PR для обеспечения:

- Чёткой аудируемости изменений
- Возможности точечного отката (revert)
- Параллельного ревью независимых изменений

#### 📋 Шаблон commit message

При создании коммита используйте следующий формат:

```text
[ПРОТОКОЛ] краткое описание изменения
```

**Примеры:**

```text
[SAM-FIX-001] синхронизация версий и глоссария
[GP-FIX-002] корректировка стратегии Пантеона (Hugo First -> Astro Later)
[SAN-FIX-003] перерасчёт бюджета БД и лимитов Supabase Free
[SAN-FIX-004] унификация типов данных для 152-ФЗ (bytea)
[MIG-FIX-005] разделение треков миграции и внедрения САН
[LIC-FIX-006] настройка Dual Licensing (CC BY-SA 4.0)
[DOCS-CHORE-007] синхронизация README.md
```

#### 🔀 Шаблон Pull Request

При создании PR заполните тело согласно шаблону `.github/PULL_REQUEST_TEMPLATE.md`:

```markdown
## Протокол
[ПРОТОКОЛ-XXX] — см. Протокол Архитектурных Изменений (ПАИ)

## Описание изменений
- Пункт 1: что изменено
- Пункт 2: что изменено
- Пункт 3: что изменено

## Затронутые манифесты
- [x] САМ.md
- [ ] САН.md
- [ ] ГРЕК-ПАНТЕОН.md
- [ ] СУМКа.md
- [ ] МИГРАЦИЯ.md
- [ ] ЛИЦ.md

## Проверка соответствия
- [ ] Не противоречит принципам САМ
- [ ] Соблюдены требования 152-ФЗ (если применимо)
- [ ] Использована Cloud-Only разработка (Web UI)
- [ ] Пройдена проверка markdownlint (если применимо)

## Тестирование
- [ ] Изменения проверены визуально на GitHub
- [ ] Отсутствуют ошибки линтера (markdownlint, если применимо)
```

#### 🤖 Автоматические проверки (GitHub Actions)

После создания PR автоматически запускаются:

1. **`architecture-check.yml`** — валидация соответствия САМ
2. **`protocol-check.yml`** — проверка префикса ветки и PR
3. **`markdownlint-cli2-action`** — проверка форматирования Markdown
4. **`sync-manifests.yml`** — подготовка рассылки в зависимые репозитории

**Статусы PR:**

- 🟡 `⏳ ожидает проверки` — GitHub Actions запущены
- 🟢 `✅ готов к ревью` — все проверки пройдены
- 🔴 `🚫 протокол нарушен` — обнаружены нарушения (см. комментарии бота)
- 🔴 `⚠️ нет префикса` — некорректное имя ветки

#### ✅ Процесс мержа

После получения **минимум 1 approve** от Архитектурного комитета:

1. Выберите метод мержа: **Squash and merge** (для сохранения linear history)
2. Убедитесь, что commit message содержит префикс протокола
3. Нажмите **Confirm squash and merge**
4. Удалите ветку после мержа (Delete branch)

#### ⚠️ Частые ошибки и их последствия

| Ошибка | Последствие | Решение |
|--------|-------------|---------|
| Прямой коммит в `main` | PR не создан, бот выставит label `🚫 протокол нарушен` | Всегда выбирайте "Create a new branch" |
| Некорректное имя ветки (без префикса) | `protocol-check.yml` упадёт с ошибкой | Переименуйте ветку или создайте новую |
| Несколько протоколов в одном PR | Нарушение атомарности, бот заблокирует мерж | Разделите на отдельные PR |
| Пропущен шаблон PR | Бот не сможет провести автоматическую проверку | Заполните все секции шаблона |
| Ошибки markdownlint | `markdownlint-cli2-action` упадёт с exit code 1 | Исправьте форматирование согласно MD-правилам |

#### 🔄 Пример полного рабочего процесса

**Задача:** Выполнить протокол `[SAM-FIX-001]`

**Шаги:**

1. Откройте `САМ.md` в GitHub Web UI
2. Внесите изменения согласно протоколу
3. Прокрутите вниз до секции "Commit changes"
4. Выберите **"Create a new branch for this commit and start a pull request"**
5. Введите имя ветки: `fix/SAM-FIX-001-version-sync`
6. Нажмите **Propose changes**
7. В открывшемся окне PR:
   - Заголовок: `[SAM-FIX-001] Синхронизация версионирования и глоссария`
   - Заполните тело PR по шаблону
8. Нажмите **Create pull request**
9. Дождитесь прохождения GitHub Actions (обычно 1-2 минуты)
10. После получения approve — выполните Squash and merge
11. Удалите ветку `fix/SAM-FIX-001-version-sync`

**Результат:** Изменение успешно интегрировано в `main` с полной аудируемостью.
