## Инструкции для ИИ-агентов

> **ВАЖНО:** Этот файл обязателен к прочтению для всех ИИ-агентов
> (Claude, GPT, Gemini и др.), работающих с репозиториями экосистемы `blago-nko`.

Настоящий документ устанавливает единые стандарты поведения ИИ-агентов при работе с кодом, манифестами и инфраструктурой экосистемы. Все правила основаны на принципах Системного Архитектурного Манифеста (САМ) и подчинены ему.

## 🌩️ Облачная разработка (Cloud-Only Development)

Вся разработка в экосистеме `blago-nko` ведётся **исключительно в облаке**.

Локальная среда разработки признаётся источником рисков:

- утечки токенов и секретов на рабочие машины;
- неконтролируемого расползания архитектурных правок;
- невозможности аудита изменений на уровне Pull Request.

### 1. ЗАПРЕЩЕНО

- Локальная разработка на рабочей машине.
- Клонирование репозиториев на локальный диск (`git clone`).
- Использование локальных IDE (VS Code desktop, IntelliJ IDEA, WebStorm и т.д.).
- Локальные коммиты и push (`git commit`, `git push`) из терминала локальной машины.
- Хранение Personal Access Tokens в локальных конфигурациях, `.env`-файлах или keyring ОС.
- Прямой коммит в ветку `main` любого репозитория экосистемы.

### 2. ОБЯЗАТЕЛЬНО

- **Редактирование кода и манифестов** — в браузере: `github.dev` (клавиша `.` на странице репозитория), `vscode.dev` или классический GitHub Web UI (карандаш).
- **Пакетная обработка** (sitemap, миграция данных, ETL, фиды) — в **Google Colab** или **GitHub Actions**.
- **Взаимодействие с репозиториями из скриптов** — через **GitHub API** с Personal Access Token.
- **Аутентификация** — через GitHub OAuth (для Web UI) или PAT (для Colab/API).
- **Обработка данных** — в RAM, без сохранения на диск локальной машины.

## 🧩 Формат выдачи кода ИИ-агентом

ИИ-агент **ОБЯЗАН** выдавать код **по частям (ячейками)** для Google Colab.
Один монолитный скрипт вместо набора ячеек — нарушение стандарта.

### Стандартная структура ответа с кодом

- **Ячейка 1 — Настройки:** импорты, токен, константы, проверка токена.
- **Ячейка 2 — Данные:** тексты, шаблоны, содержимое файлов.
- **Ячейка 3 — Функции:** вспомогательные функции работы с GitHub API.
- **Ячейка 4 — Выполнение:** основной цикл / главная логика.
- **Ячейка 5 — Проверка:** контроль результата (GET-запросы, отчёт).

### Правила оформления ячеек

1. Каждая ячейка нумеруется и имеет заголовок (`Ячейка N — ...`).
2. Порядок запуска указывается явно («выполняйте по порядку»).
3. В конце каждой ячейки — `print("✅ Ячейка N готова...")` для контроля.
4. Токен указывается **ТОЛЬКО** в ячейке 1 (настройки), нигде больше.
5. Ячейка либо самодостаточна, либо явно ссылается на предыдущие («использует переменные из ячейки 1»).
6. Длинные тексты и шаблоны выносятся в отдельную ячейку-данные, а не встраиваются в логику.
7. Если задача простая — допустимо 2–3 ячейки вместо пяти, но разделение «настройки / выполнение / проверка» сохраняется.

### Причины стандарта ячеек

- Пользователь работает в Colab без локального окружения.
- Частичный перезапуск при ошибках без потери состояния.
- Прозрачность: видно, какой шаг что делает.
- Безопасность: токен изолирован в одной ячейке.
- Повторяемость: любой агент может воспроизвести результат.

## 🔐 Рабочий процесс (шаблон для Colab)

```python
import requests
import base64

GITHUB_TOKEN = "ваш_токен"  # https://github.com/settings/tokens
OWNER = "blago-nko"

HEADERS = {
    "Authorization": f"token {GITHUB_TOKEN}",
    "Accept": "application/vnd.github.v3+json",
    "Content-Type": "application/json"
}

def read_file(repo, path):
    url = f"https://api.github.com/repos/{OWNER}/{repo}/contents/{path}"
    resp = requests.get(url, headers=HEADERS)
    if resp.status_code == 200:
        return base64.b64decode(resp.json()['content']).decode('utf-8')
    return None

def write_file(repo, path, content, message, branch="main"):
    url = f"https://api.github.com/repos/{OWNER}/{repo}/contents/{path}"
    sha_resp = requests.get(url, headers=HEADERS)
    sha = sha_resp.json().get('sha') if sha_resp.status_code == 200 else None
    data = {
        "message": message,
        "content": base64.b64encode(content.encode('utf-8')).decode('utf-8'),
        "branch": branch
    }
    if sha:
        data["sha"] = sha
    resp = requests.put(url, headers=HEADERS, json=data)
    return resp.status_code in [200, 201]

    Этот шаблон запрещено запускать локально — только в Google Colab или GitHub Actions.

## 5. ПОРЯДОК ВНЕСЕНИЯ ИЗМЕНЕНИЙ В МАНИФЕСТЫ (Codespaces-Only Policy)

Репозиторий `blago-nko/manifests` — высший орган архитектурного права экосистемы. Все изменения манифестов (САМ, САН, СУМКа, ГРЕК-ПАНТЕОН, МИГРАЦИЯ, ЛИЦ, AGENTS) вносятся **исключительно через GitHub Codespaces**. Локальное клонирование и `git push` вне Codespaces КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ. GitHub Web UI допускается только для точечных опечаток, не меняющих смысл.

### 5.1. Почему только Codespaces
- **Cloud-Only:** локальных копий манифестов не существует;
- **Единая среда:** Python, `gh` и markdownlint предустановлены — проверки совпадают с CI;
- **Аудируемость:** ветка → PR → статус-чеки → мерж;
- **Человек и ИИ в одном контуре:** ИИ готовит правки и команды, человек выполняет их в том же окне.

### 5.2. Пошаговая инструкция для Человека
1. **Откройте Codespaces:** на странице репозитория **Code → Codespaces → «+»** (или существующее пространство на https://github.com/codespaces).
2. **Включите терминал:** в окне «Вы доверяете авторам…» нажмите синюю кнопку доверия.
3. **Создайте ветку:** `git pull origin main && git checkout -b fix/<имя>`.
4. **Внесите правки** в редакторе (левая панель), сохраните `Ctrl+S`.
5. **Закоммитьте и запушьте:**
    git add <файлы>
    git commit -m "fix(область): описание (ПРОТОКОЛ-XXX)"
    git push -u origin fix/<имя>
6. **Создайте PR:** `gh pr create`, тело — по шаблону `.github/PULL_REQUEST_TEMPLATE.md`.
7. **Чеки и ревью:** вкладка **Checks** зелёная; approve Архитектурного комитета.
8. **Мерж:** **Squash and merge**, удалить ветку.
9. **Контроль:** дождаться `chore(INFRA): auto-sync manifests metadata [skip ci]`, проверить результат в `main`.
10. **Остановите Codespace:** https://github.com/codespaces → «⋯» → **Stop/Delete**.

### 5.3. Роль ИИ-агента
ИИ-агент не вносит коммиты напрямую. Он выдаёт: (а) точные правки «найти → заменить», (б) готовые команды терминала из п. 5.2, (в) тело PR по шаблону. Человек выполняет их в Codespaces.

### 5.4. Автообновление md-файлов
Метаданные манифестов (шапка, таблица реквизитов, блок «Связанные документы») и таблица `README.md` перегенерируются скриптом `scripts/sync_manifests.py` из реестра `docs/manifests.yaml`: при каждом пуше в `main`, ежедневно по расписанию и вручную через Actions (workflow_dispatch). Тело манифестов редактируется только Человеком через PR — это источник правды.

#### 📝 Правило атомарности

**1 протокол = 1 ветка = 1 PR.**

Запрещено объединять несколько протоколов в одном PR. Каждый протокол из ПАИ (Протокола Архитектурных Изменений) должен быть выполнен отдельным PR для обеспечения:

- чёткой аудируемости изменений;
- возможности точечного отката (revert);
- параллельного ревью независимых изменений.

## Ячейка 20 — Автоматические проверки (GitHub Actions)

```markdown
#### 🤖 Автоматические проверки (GitHub Actions)

После создания PR автоматически запускаются:

1. **`architecture-check.yml`** — валидация соответствия САМ.
2. **`protocol-check.yml`** — проверка префикса ветки и PR.
3. **`markdownlint-cli2-action`** — проверка форматирования Markdown.
4. **`sync-manifests.yml`** — подготовка рассылки в зависимые репозитории.
5. **`sync-readme.yml`** — обновление таблицы версий в README из YAML-метаданных (SAM-INFRA-008).

**Статусы PR:**

- 🟡 `⏳ ожидает проверки` — GitHub Actions запущены.
- 🟢 `✅ готов к ревью` — все проверки пройдены.
- 🔴 `🚫 протокол нарушен` — обнаружены нарушения (см. комментарии бота).
- 🔴 `⚠️ нет префикса` — некорректное имя ветки.

#### ✅ Процесс мержа

После получения **минимум 1 approve** от Архитектурного комитета:

1. Выберите метод мержа: **Squash and merge** (для сохранения linear history).
2. Убедитесь, что commit message содержит префикс протокола.
3. Нажмите **Confirm squash and merge**.
4. Удалите ветку после мержа (Delete branch).

#### ⚠️ Частые ошибки и их последствия

| Ошибка | Последствие | Решение |
|--------|-------------|---------|
| Прямой коммит в `main` | PR не создан, бот выставит label `🚫 протокол нарушен` | Всегда выбирайте "Create a new branch" |
| Некорректное имя ветки (без префикса) | `protocol-check.yml` упадёт с ошибкой | Переименуйте ветку или создайте новую |
| Несколько протоколов в одном PR | Нарушение атомарности, бот заблокирует мерж | Разделите на отдельные PR |
| Пропущен шаблон PR | Бот не сможет провести автоматическую проверку | Заполните все секции шаблона |
| Ошибки markdownlint | `markdownlint-cli2-action` упадёт с exit code 1 | Исправьте форматирование согласно MD-правилам |
| Кириллица в имени ветки | Git-совместимость, конфликты на Windows/macOS | Используйте только латиницу (стандарт SAM-REF-007) |

#### 🔄 Пример полного рабочего процесса

**Задача:** Выполнить протокол `[SAM-FIX-001]`

**Шаги:**

1. Откройте `САМ.md` в GitHub Web UI.
2. Внесите изменения согласно протоколу.
3. Прокрутите вниз до секции "Commit changes".
4. Выберите **"Create a new branch for this commit and start a pull request"**.
5. Введите имя ветки: `fix/SAM-FIX-001-version-sync`.
6. Нажмите **Propose changes**.
7. В открывшемся окне PR:
   - Заголовок: `[SAM-FIX-001] Синхронизация версионирования и глоссария`
   - Заполните тело PR по шаблону.
8. Нажмите **Create pull request**.
9. Дождитесь прохождения GitHub Actions (обычно 1–2 минуты).
10. После получения approve — выполните Squash and merge.
11. Удалите ветку `fix/SAM-FIX-001-version-sync`.

**Результат:** Изменение успешно интегрировано в `main` с полной аудируемостью.

### Шаг 1. GitHub Codespaces
> Откройте https://github.com/blago-nko/manifests → `<> Code` → **Codespaces** → **Create codespace on main**

### Шаг 2. Одна команда в терминале
> Запустите патч-скрипт: он сам применит правки, создаст ветку, сделает

### Шаг 3. Merge
> Откройте выведенную ссылку → проверьте **Files changed** → **Merge pull request**.

> Вкладка **Actions** → **🏗️ Применить архитектурный патч** → **Run workflow** → выбрать протокол → **Run**.
