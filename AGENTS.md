# Инструкции для ИИ-агентов

> **ВАЖНО:** Этот файл обязателен к прочтению для всех ИИ-агентов
> (Claude, GPT, Gemini и др.), работающих с этим репозиторием.

## 🌩️ Облачная разработка (Cloud-Only Development)

Вся разработка в экосистеме blago-nko ведётся **исключительно в облаке**.

### Обязательные правила

1. **ЗАПРЕЩЕНО:**
   - Локальная разработка на рабочей машине
   - Клонирование репозиториев на локальный диск (`git clone`)
   - Использование локальных IDE (VS Code, IntelliJ и т.д.)
   - Локальные коммиты и push (`git commit`, `git push`)

2. **ОБЯЗАТЕЛЬНО:**
   - Google Colab или Jupyter notebooks для всей разработки
   - GitHub API для всех изменений файлов
   - Personal Access Tokens для аутентификации
   - Обработка всех данных в памяти (RAM), без сохранения на диск

## 🧩 Формат выдачи кода ИИ-агентом

ИИ-агент ОБЯЗАН выдавать код **по частям (ячейками)** для Google Colab.
Один монолитный скрипт вместо набора ячеек — нарушение стандарта.

### Стандартная структура ответа с кодом

- **Ячейка 1 — Настройки:** импорты, токен, константы, проверка токена
- **Ячейка 2 — Данные:** тексты, шаблоны, содержимое файлов
- **Ячейка 3 — Функции:** вспомогательные функции работы с GitHub API
- **Ячейка 4 — Выполнение:** основной цикл / главная логика
- **Ячейка 5 — Проверка:** контроль результата (GET-запросы, отчёт)

### Правила оформления ячеек

1. Каждая ячейка нумеруется и имеет заголовок («Ячейка N — ...»).
2. Порядок запуска указывается явно («выполняйте по порядку»).
3. В конце каждой ячейки — `print("✅ Ячейка N готова...")` для контроля.
4. Токен указывается ТОЛЬКО в ячейке 1 (настройки), нигде больше.
5. Ячейка либо самодостаточна, либо явно ссылается на предыдущие
   («использует переменные из ячейки 1»).
6. Длинные тексты и шаблоны выносятся в отдельную ячейку-данные,
   а не встраиваются в логику.
7. Если задача простая — допустимо 2–3 ячейки вместо пяти,
   но разделение «настройки / выполнение / проверка» сохраняется.

### Причины

- Пользователь работает в Colab без локального окружения
- Частичный перезапуск при ошибках без потери состояния
- Прозрачность: видно, какой шаг что делает
- Безопасность: токен изолирован в одной ячейке

## 🔐 Рабочий процесс (шаблон для Colab)

```python
import requests
import base64

GITHUB_TOKEN = "ваш_токен"  # https://github.com/settings/tokens
OWNER = "blago-nko"

HEADERS = {
    "Authorization": f"token {GITHUB_TOKEN}",
    "Accept": "application/vnd.github.v3+json",
    "Content-Type": "application/json"
}

def read_file(repo, path):
    url = f"https://api.github.com/repos/{OWNER}/{repo}/contents/{path}"
    resp = requests.get(url, headers=HEADERS)
    if resp.status_code == 200:
        return base64.b64decode(resp.json()['content']).decode('utf-8')
    return None

def write_file(repo, path, content, message):
    url = f"https://api.github.com/repos/{OWNER}/{repo}/contents/{path}"
    sha_resp = requests.get(url, headers=HEADERS)
    sha = sha_resp.json().get('sha') if sha_resp.status_code == 200 else None
    data = {
        "message": message,
        "content": base64.b64encode(content.encode('utf-8')).decode('utf-8'),
        "branch": "main"
    }
    if sha:
        data["sha"] = sha
    resp = requests.put(url, headers=HEADERS, json=data)
    return resp.status_code in [200, 201]
```

## 🔑 Безопасность токенов

## 5. ПОРЯДОК ВНЕСЕНИЯ ИЗМЕНЕНИЙ В МАНИФЕСТЫ (Manifests-Only Web UI Policy)

Репозиторий `blago-nko/manifests` является высшим органом архитектурного права экосистемы. Для обеспечения максимальной прозрачности, аудируемости и защиты от несанкционированных локальных правок вводится строгая политика.

### 🚫 Жесткий запрет на локальную разработку манифестов

ИИ-агентам и разработчикам **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО**:
1. Клонирировать репозиторий `blago-nko/manifests` на локальные машины.
2. Создавать локальные ветки (`git checkout -b`) для редактирования текстов манифестов.
3. Делать локальные коммиты и выполнять `git push` в этот репозиторий из IDE (VSCode, Cursor и т.д.) или терминала.

### ✅ Единственный легальный способ: GitHub Web UI

Все изменения в манифесты (САМ, САН, СУМКа, ГРЕК-ПАНТЕОН, МИГРАЦИЯ, ЛИЦ) вносятся **исключительно через встроенный редактор GitHub (Web UI)** по следующему протоколу:

1. **ИИ-агент генерирует точечные инструкции** (какой файл открыть, какую строку найти, на какой текст заменить) или предоставляет **готовый блок Markdown-кода**.
2. **Пользователь (Человек)** открывает нужный файл на GitHub, нажимает `Edit this file` (карандаш), вставляет изменения и создает коммит прямо в браузере.
3. **Создание ветки:** Коммит делается не в `main`, а в новую ветку, создаваемую через Web UI (опция *Create a new branch for this commit and start a pull request*). Имя ветки должно строго соответствовать протоколу: `chore/SAM-XXX-description` или `fix/MIG-XXX-description`.
4. **Pull Request:** Из Web UI создается PR, в тело которого вставляется сгенерированный ИИ-агентом шаблон с описанием изменений и затронутыми разделами.

### 🤖 Поведение ИИ-агента при запросе на изменение манифеста

Если пользователь или другой агент просит изменить манифест, ИИ-агент обязан:
1. **Не пытаться** применять изменения к локальным файлам (так как их не должно быть на диске).
2. Вывести в чат блок:

   ```text
   ⚠️ ТРЕБУЕТСЯ ПРАВКА МАНИФЕСТА (Web UI Protocol)
   Файл: [Имя файла.md]
   Префикс протокола: [SAM-/SAN-/GP-/MIG-/LITS-CHORE-XXX]
   
   ИНСТРУКЦИЯ ДЛЯ ЧЕЛОВЕКА:
   1. Перейдите по ссылке: [URL файла на GitHub]
   2. Нажмите карандаш (Edit).
   3. Найдите блок: `[старый текст]`
   4. Замените на:
   [новый готовый блок Markdown]
   5. Внизу выберите "Create a new branch" и назовите её: `chore/префикс-описание`.
   6. Нажмите "Propose changes".
