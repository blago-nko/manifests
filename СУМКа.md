## РАЗДЕЛ 1. АРХИТЕКТУРА КОНТЕНТНОГО КОНВЕЙЕРА

### 1.1 Источники контента

| Источник | Тип | Обработка |
|----------|-----|-----------|
| RSS/XML Blogger | Автоматический | Парсинг через `build_static_rss.py` |

### 1.2 Контекстный билдер (ИИ-паспорт статьи)

Каждая публикация получает структурированный Тематический паспорт (адаптирован под специфику каждого из 14 сайтов):

**Пример для blagorussia.ru**

```yaml
тематический_паспорт:
  ключевые_сущности: [список из 3-5]
  суть_в_3_пунктах: [краткое резюме]
  география: [регионы/города]
  источники: [ссылки на первоисточники]
  автор: {
    name: "Бобров А.В.",
    role: "founder",
    sameAs: ["https://blagorussia.ru/team/founder/"]
  }
  image_metadata:
    source_url: "https://..."
    author: "..."
    license: "CC BY 4.0"
  паттерн_url: "evergreen" | "news"
```

### 1.3 Лингвистический шлюз качества

- **Порог публикации:** score ≥ 8 (из 10)

```typescript
interface IContentQualityService {
  generateDraft(context: string): Promise<string>;
  audit(text: string): Promise<{score: number; fixed: string; reason: string}>;
  processAndValidate(context: string, entityType: string): Promise<ContentResult>;
}
```

- **Реализация:** Gemini API через `ContentQualityService` (трёхэтапный пайплайн: Генерация → Аудит → Публикация)
- **Низкий score (< 8):** запись в `content_drafts` на ручную проверку администратором.

### 1.4 Мульти-ролевая атрибуция (Multi-Role Entity Pattern)

Одно физическое лицо представляется как три отдельные сущности с разными ролями:

| Роль | URL | JSON-LD тип | Контент |
|------|-----|-------------|---------|
| Основатель НКО | `blagorussia.ru/team/founder/` | Person + OrganizationFounder | Биография, миссия |
| Автор-эксперт | `obrazslov.ru/authors/[slug]` | Person + Journalist | Статьи, аналитика |
| Администратор САН | `can.blagorussia.ru/staff/[slug]` | Person + Employee | Новости платформы |

> ⚠️ **Уточнение:**
> В целях консолидации E-E-A-T (ссылочного веса и экспертного авторитета) роли «Исследователь», «Компилятор», «Редактор» и «Журналист» НЕ создаются как отдельные URL-сущности, а агрегируются внутри единой публичной персоны «Автор-эксперт» (`/authors/[slug]`).
>
> Различие между этими ролями осуществляется семантически, через массив `hasOccupation` в JSON-LD разметке (Person → hasOccupation → Occupation).
>
> Если роль «Редактор» или «Переводчик» принадлежит третьему лицу (например, античному автору или гостевому автору), это лицо фиксируется не через Multi-Role Entity, а через поля `contributor` / `source` в Тематическом паспорте и JSON-LD.

**JSON-LD пример:**

```json
{
  "@context": "https://schema.org",
  "@type": "Article",
  "author": {
    "@type": "Person",
    "name": "Бобров Александр Валентинович",
    "url": "https://obrazslov.ru/authors/bobrov",
    "hasOccupation": [
      { "@type": "Occupation", "name": "Руководитель НКО" },
      { "@type": "Occupation", "name": "Историк-исследователь" },
      { "@type": "Occupation", "name": "Главный редактор" },
      { "@type": "Occupation", "name": "Журналист" }
    ],
    "worksFor": {
      "@type": "Organization",
      "name": "НП «Общественное благополучие»"
    },
    "sameAs": [
      "https://blagorussia.ru/team/founder/",
      "https://nasa-istoria.blagorussia.ru/2022/01/bobrov-aleksandr-valentinovich-biografiya.html"
    ]
  }
}
```

### 5.6 Регламент обработки изображений (Image Sanitization Pipeline)

**Краткое описание этапов:**

1. EXIF-очистка (`exiftool -all=`)
2. Конвертация в WebP/AVIF (`sharp`/`cwebp`)

4. Детекция дубликатов (pHash + Hamming distance)

### 5.7 Регламент атрибуции изображений для grekpanteon

Обязательное указание источника изображения в `alt` и JSON-LD `ImageObject`.

**Обоснование:**

1. **E-E-A-T:** Google и ИИ-поисковики приоритизируют контент с прозрачной атрибуцией источников
2. **Авторское право:** Защита от претензий по DMCA
3. **GEO:** ИИ-поисковики цитируют только источники с явным `author`, `license`, `url`

**Источники изображения (3 уровня):**

1. **Google Таблица (основной):**
   - 1.a. Таблица `sources` содержит поле `external_url`
   - 1.b. Связь: `characters.source_id` → `sources.id` → `sources.external_url`
   - 1.c. Скрипт `build_hugo_from_db.py` автоматически подтягивает URL
2. **Wikidata API (обогащение):**
   - 2.a. Для персонажей с `wikidata_id` скрипт `grekpanteon_pipeline.py` получает:
     - 2.a.i. `wdt:P18` (изображение) → URL файла на Wikimedia Commons
     - 2.a.ii. `wdt:P551` (место жительства) → координаты
   - 2.b. Автоматическая генерация JSON-LD
3. **Ручная атрибуция (для эксклюзивных фото):**
   - 3.a. Для фото Боброва А.В. — жёстко зафиксировано в Тематическом паспорте
   - 3.b. Поле `photographer: "Бобров А.В."` в YAML-frontmatter

Для всех изображений (не только grekpanteon) обязательна разметка `ImageObject` с полями `author`, `license`, `source` в JSON-LD.

**Техническая реализация:**

`scripts/image_source_extractor.py`

```python
def extract_image_source(character_id, db_connection):
    cursor = db_connection.execute(
        "SELECT source_id FROM characters WHERE id = ?", (character_id,)
    )
    source_id = cursor.fetchone()[0]
    cursor = db_connection.execute(
        "SELECT external_url, author_name, license_url FROM sources WHERE id = ?",
        (source_id,)
    )
    source = cursor.fetchone()
    return {
        "contentUrl": f"https://grekpanteon.obrazslov.ru/images/{character_id}.webp",
        "author": {"@type": "Person", "name": source[1] or "Неизвестен"},
        "license": source[2] or "https://creativecommons.org/licenses/by-sa/4.0/",
        "source": source[0]
    }
```

| 1+ | Архив (вечное хранение) | LCP-ускорение для карточек САН |

**Защита от vendor lock-in:**

- Скрипт `migrate_blogger_to_r2.py`
- Еженедельный бэкап метаданных в `shared-assets/blogger_image_metadata.json` (Git)
- GitHub Actions: `.github/workflows/backup_blogger_metadata.yml`

> **Примечание:** Сайт САН (`can.blagorussia.ru`) размещён на отдельном GitHub-аккаунте `can-secure-dev`. Это обеспечивает изоляцию ПДн-контура и независимый CI/CD пайплайн. Подробнее см. Приложение В САМ.

### 8.5 Структура sitemap для grekpanteon

> ⚠️ **КРИТИЧЕСКОЕ ИЗМЕНЕНИЕ (5 июля 2026 г.):**
> Sitemap для grekpanteon формируется по принципу батчинга по ID (5000 URL на файл), а НЕ по коленам (поколениям) или алфавиту.

**Обоснование:** Колено (generation) может меняться при обновлении генеалогических данных, что приводит к 404 ошибкам и пессимизации Google. Алфавитное распределение неравномерно (буква «А» — 2000 персонажей, буква «Я» — 50).

**Официальные лимиты sitemap:**

- 50 000 URL на один файл
- 50 МБ на файл (несжатый)
- Без ограничений на число файлов в sitemap_index

**Новая структура `sitemap_index.xml`:**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<sitemapindex xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <sitemap>
    <loc>https://grekpanteon.obrazslov.ru/sitemap-mythological-characters.xml</loc>
    <lastmod>2026-07-09</lastmod>
  </sitemap>
  <sitemap>
    <loc>https://grekpanteon.obrazslov.ru/sitemap-historical-characters-001.xml</loc>
    <lastmod>2026-07-09</lastmod>
  </sitemap>
  <!-- ... (по числу батчей) -->
</sitemapindex>
```

**Скрипт генерации:** `scripts/generate_sitemaps.py` (батчинг по 5000 URL с OFFSET/LIMIT).

### 8.6 Автоматический ping поисковиков

**Скрипт:** `scripts/ping_search_engines.py`

```python
import requests

PING_URLS = {
    "google": "https://www.google.com/ping?sitemap={}",
    "yandex": "https://yandex.com/ping?sitemap={}",
    "bing": "https://www.bing.com/ping?sitemap={}",
    "indexnow": "https://api.indexnow.org/indexnow?url={}&key={}"
}

def ping_all(sitemap_url, domain):
    for engine, template in PING_URLS.items():
        try:
            url = template.format(sitemap_url)
            response = requests.get(url, timeout=10)
            log_ping(engine, domain, response.status_code)
        except Exception as e:
            log_error(engine, domain, str(e))
```
